## 1 引言

### 1.1 编写目的

本文档用于统一 FreeIDX 论坛的技术实现口径，作为开发、评审、测试与运维的依据。文档聚焦**架构决策与硬约束**，不展开具体代码实现细节；接口字段以 `packages/shared` 中的类型定义为最终事实源。

### 1.2 适用范围

V1 功能范围如下：

| 领域 | 包含能力 |
|---|---|
| 内容浏览 | 首页/版块主题列表（分页、排序、置顶合并）、主题详情、回帖分页、引用、关键词高亮、精华筛选、已读标记、二级导航 |
| 内容生产 | 发帖、回帖、编辑、删除、移动版块、富文本编辑器、插入代码、附件上传/下载 |
| 账号体系 | 注册、登录、退出、邮箱验证码、找回密码、个人中心、用户主页、头像 |
| 权限与版务 | 用户组 × 版块 × 版主三层权限、置顶/精华/关闭/移动/删除、批量版务、modlog 审计 |
| 站点管理 | 站点设置、版块与权限矩阵、用户、用户组、主题管理、扩展管理、缓存清理、运行统计 |
| 会员与交易 | 积分账本、付费附件、VIP 计划、订单与支付通道插件 |
| 收录与增长 | 爬虫预渲染、sitemap、结构化数据、GEO 策略、广告位与 AdSense |
| 平台能力 | 多语言、三层缓存、定时任务、异步队列、SMTP 邮件、插件与主题机制 |

V1 明确不包含：

- IE 降级提示页（目标浏览器为现代浏览器）。
- 跨站单点登录（后续如需，按标准 OAuth/JWT 重做）。
- 第三方插件市场与源码级文件覆盖。
- 搜索、标签、第三方登录等长尾能力（保留扩展点，搜索列入 M6 可选）。
- 历史版本升级脚本与 Web 安装向导（部署即安装，存量数据走迁移工具）。

### 1.3 术语与缩略语

| 术语 | 说明 |
|---|---|
| Worker | Cloudflare Workers，无服务器运行时，承载后端 API |
| Pages | Cloudflare Pages，承载前端静态资源 |
| D1 / KV / R2 | Cloudflare 关系型数据库 / 键值存储 / 对象存储 |
| SPA | 单页应用，普通用户访问形态 |
| 预渲染 | 写入期生成静态 SEO HTML，供爬虫读取，非请求期 SSR |
| runlevel | 站点运行级别 0–5，全局访问闸门 |
| 三层权限 | 用户组权限位 × 版块 access 矩阵 × 版主名单 |
| 扩展（插件） | 通过钩子、路由、定时任务、组件插槽扩展核心能力的独立模块 |
| 主题 | 参与前端构建的完整外观代码，可替换布局与页面 |
| L0/L1/L2/L-1 | Isolate 内存缓存 / KV 缓存 / D1 缓存表 / 边缘响应缓存 |

## 2 系统概述

### 2.1 建设目标

FreeIDX 论坛全站运行于 Cloudflare 免费层，零服务器运维成本，同时保证论坛功能完整、接口契约稳定、具备可持续扩展能力。具体目标：

1. 前后端同域部署，数据层 D1/KV/R2，无自建服务器。
2. 覆盖论坛核心闭环：浏览、发帖、权限、版务、后台运营。
3. 满足搜索引擎收录硬需求，兼顾 AI 引擎（GEO）可读性。
4. 通过扩展机制承载支付、SEO/GEO、广告等可选能力，可独立启停。

### 2.2 平台约束

| 服务 | 免费额度（参考） | 对设计的影响 |
|---|---|---|
| Workers | 10 万请求/天；CPU 10ms/请求（免费层固定）；请求体 100MB | API 必须轻量；重计算移至写入期或异步路径；密码哈希迭代数受 10ms 约束 |
| Pages | 请求与带宽不限，每月 500 次构建 | 前端托管无容量压力 |
| D1 | 单库 500MB；500 万行读取/天、10 万行写入/天；单次调用最多 50 条查询；单行 2MB | 高频读走缓存；聚合查询用 `DB.batch()`；计数合并写入 |
| KV | 10 万读/天、1 万写/天 | 仅存低频写、高频读的全局配置，禁止存会话 |
| R2 | 10GB 存储；A 类 100 万/月、B 类 1000 万/月；无出站流量费 | 附件与头像存储，Worker 代理读取并加缓存 |
| Cron Triggers | 免费 | 承担定时任务 |
| Queues | 需付费计划 | 不使用，采用 D1 队列表 |

### 2.3 架构原则

1. **免费层优先**：所有选型零成本，超限时提供平滑付费升级路径。
2. **功能完整优先于架构新颖**：权限模型、响应信封、URL 语义保持稳定。
3. **无服务器状态**：Worker 不持有本地状态，会话、文件、统计全部落 D1/R2。
4. **写路径最短，读路径有缓存**：D1 写入额度是首要稀缺资源。
5. **契约先行**：共享类型、错误码、插件契约先冻结，前后端并行开发。
6. **计算前置**：内容格式化、SEO HTML 等计算在写入期完成，读路径仅做 I/O 与序列化。

### 2.4 总体架构

```
                        ┌──────────────────────────────┐
   浏览器（现代设备）      │      Cloudflare CDN 边缘      │
        │               └──────────────┬───────────────┘
        │ 页面/静态资源                  │ /api/*、/files/* 转发
        ▼                              ▼
┌──────────────────────┐   ┌────────────────────────────────┐
│  Cloudflare Pages     │   │  Worker「freeidx-api」（Hono）  │
│  React 19 + Tailwind 4│   │  ├ 鉴权中间件（Session+JWT）     │
│  SPA + 主题体系        │◄──┤  ├ 权限引擎（组×版块×版主）      │
│  /admin/* 管理后台     │JSON│  ├ 业务路由                     │
└──────────────────────┘   │  └ Cron / 队列消费               │
        ▲                  └───────┬────────┬────────┬───────┘
        │ 图片/附件直链               │        │        │
┌───────┴────────┐          ┌────────▼──┐ ┌───▼────┐ ┌─▼──────────┐
│ Cloudflare R2   │          │ D1         │ │ KV     │ │ SMTP 服务   │
│ 附件/头像/SEO页  │          │ 核心数据    │ │ 配置缓存│ │ （账号池）   │
└────────────────┘          └───────────┘ └────────┘ └────────────┘
```

部署要点：

- Pages 只负责前端，数据全部经 `/api` 调 Worker；推荐同域部署，省去 CORS 且 Cookie 天然同域。
- 图片/附件由 Worker 流式代理 R2（`GET /files/:key`），配合 Cache API 与浏览器强缓存。
- 爬虫请求返回写入期预生成的 SEO HTML（存 R2），普通用户返回 SPA 壳。

| 层 | 选型 | 说明 |

## 3 数据设计

### 3.1 设计约定

| 语义 | D1/SQLite 落地 | 说明 |
|---|---|---|
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | tid/pid/uid 等 |
| 布尔位 | `INTEGER`（0/1） | allow* 权限位、closed |
| 时间 | `INTEGER` unix 秒 | 统一口径，避免时区与解析开销 |
| 长文本 | `TEXT` | message、message_fmt、kv.v |
| 表前缀 | `bbs_` | 与常见论坛模型对齐 |
| 索引 | 独立 `CREATE INDEX` | 组合索引按查询前缀设计 |
| 深分页 | 游标 `?before_tid=` | OFFSET 跳过行仍计入 rows_read，禁止深 OFFSET |

### 3.2 数据表清单

核心表 17 张：

| 表 | 说明 |
|---|---|
| `user` | 账号、密码哈希、salt、`token_version`、积分字段、VIP 到期时间与来源组 |
| `group` | 12 个 allow* 权限位；0/1/2/4/5/6/7 为固定组，101–105 等级组，106 VIP 组 |
| `forum` | 版块基本信息、`accesson`、`moduids`、SEO 标题/关键词 |
| `forum_access` | (fid,gid) 复合主键，5 项版块级 allow* 权限 |
| `thread` | 主题；top/closed/digest/firstpid/lastpid；反规范化 `username`/`lastusername`/`avatar` |
| `thread_top` | 置顶倒排表 |
| `post` | 帖子；`message` 原文 + `message_fmt` 渲染结果；doctype、quotepid、isfirst |
| `attach` | 附件；`filename` 存 R2 key，`status`（0 临时/1 已入库），积分价格字段 |
| `mythread` / `mypost` | 用户主题/回帖倒排索引 |
| `session` | 会话；sid/uid/fid/url/ip/useragent/last_date，支撑在线用户 |
| `modlog` | 版务审计日志 |
| `kv` | 站点设置、插件启停、启用主题等全局单键 |
| `cache` | D1 兜底缓存层（带过期时间） |
| `queue` | 异步任务队列 |
| `table_day` | 按日统计辅助表（V1 建表不启用） |
| `email_code` | 邮箱验证码；email、code、scene、expiry，不绑定登录前会话 |

业务表（随 `0001_init` 建表）：

| 表 | 说明 |
|---|---|
| `vip_plan` | VIP 计划：名称、时长、价格、权益 JSON |
| `order` | 订单：order_no、uid、plan_id、金额、币种、状态、provider、provider_ref |
| `point_log` | 积分流水：变动值、余额、原因、幂等键 |
| `card` | 卡密：批次、面值、兑换状态 |
| `ad_slot` | 广告位：位置、类型、配置 JSON、启停、排序、生效时间；schema 归核心、数据归 ads 插件 |

### 3.3 关键设计决策

**反规范化用户快照**：`thread` 冗余 `username`/`lastusername`/`avatar`，使列表页单表扫描、零 JOIN、零用户二次查询，显著降低 D1 行读取。代价是改名时需回写，属读多写少场景的既定取舍。

**lastusername 一致性规则**：回帖更新尾列、待审回帖过审补列、删除末帖回退三条路径必须与 `lastpid`/`lastuid`/`last_date` 同步写入 `lastusername`；否则列表页"最后回复"会长期显示楼主名。管理员改名通过 `waitUntil` 异步批量回写该用户相关主题，并由每日校准任务兜底自愈。

**配置存储**：

- 静态部署配置（D1/KV/R2 绑定、密钥）→ `wrangler.toml` vars / Secrets。
- 动态站点设置（站名、runlevel、注册开关、排序开关等）→ `kv` 表 `setting` 键 + JSON 值，写后失效缓存。
- 其他全局单键同样落 `kv` 表：插件启停 `extensions`、启用主题 `theme`。

**初始数据（seed）**：预置用户组（0 游客 / 1 管理员 / 2 超级版主 / 4 版主 / 5 实习版主 / 6 待验证 / 7 禁止 / 101–105 等级组），默认测试版块与 `forum_access` 矩阵，并以 CLI 创建首个管理员。

**索引与查询约束**：列表查询使用覆盖索引 `(fid,lastpid)`、`(fid,tid)`；禁止 `SELECT *`，列表查询不触及 `message`/`message_fmt`；聚合接口使用 `DB.batch()` 合并往返。

## 4 接口设计

### 4.1 通用约定

- 基础路径 `/api`；响应信封 `{ "code": 0, "message": "ok", ...data }`。
- `code < 0` 表示全局错误（如 -1 未登录），`code > 0` 表示表单级业务错误；错误码集中在 `packages/shared/codes.ts`。
- 非 GET 请求校验 `X-CSRF-Token`（与 `csrf` Cookie 双提交一致）。
- 分页参数 `?page=N`；首页/版块每页 30 条，用户主题每页 20 条。
- 所有写接口先过权限引擎，再执行 D1 写入。

### 4.2 内容与用户接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/bootstrap` | 版块树、当前用户、二级导航、插件贡献字段，一次下发 |
| GET | `/api/threads?fid&page&digest` | 首页聚合列表，服务端完成权限过滤与置顶合并 |
| GET | `/api/forums/{fid}/threads?page&orderby&digest` | 版块主题列表，orderby=tid/lastpid |
| GET | `/api/thread-form?fid` | 可发帖版块清单（allowthread 过滤） |
| POST | `/api/threads` | 发帖；校验 Turnstile 与 allowthread，创建首帖并回填 firstpid |
| GET | `/api/threads/{tid}?page&keyword` | 主题详情；batch 聚合帖子、附件、权限位；浏览量异步 +1 |
| POST | `/api/threads/{tid}/posts` | 回帖；closed 帖非版主禁回，quotepid 引用同帖生效 |
| PUT | `/api/posts/{pid}` | 编辑；首帖可同时改标题/版块 |
| DELETE | `/api/posts/{pid}` | 删除；首帖级联删除主题并回退 lastpid/lastusername |
| POST | `/api/auth/login` | 邮箱或用户名 + 密码登录 |
| POST | `/api/auth/register` | 注册，可选邮箱验证码 |
| POST | `/api/auth/logout` | 退出 |

### 4.5 权限引擎

`core/access.ts` 是权限的单一事实源，所有读写接口统一经其判定：

```
普通操作 forumAccessUser(fid, gid, 'allowread|allowthread|allowpost|allowattach|allowdown')
  forum.accesson == 0 → 仅 group.allow*
  forum.accesson == 1 → group.allow* && forum_access[fid][gid].allow*

版务操作 forumAccessMod(fid, gid, uid, 'allowtop|allowmove|allowupdate|allowdelete')
  gid == 1 || gid == 2 → 直接通过
  gid == 3/4/5 → group.allow* && uid ∈ forum.moduids

作者叠加：allowupdate/allowdelete = (当前 uid == 帖子 uid && 组允许) || forumAccessMod(...)
全局闸门：runlevel 0 正常 … 5 仅管理员；未登录受限页跳转登录
```

列表与详情返回前执行三级过滤：`forumListAccessFilter` / `threadListAccessFilter` / `postListAccessFilter`。用户组自动升级：发帖/回帖成功后，若 `gid >= 100`，按 `posts + threads` 落入等级组 `creditsfrom/creditsto` 区间自动换组，并失效用户缓存。

## 5 认证与安全

### 5.1 双轨会话

- **Session 轨**：登录写 D1 `session` 行（sid、uid、ip、url、useragent、last_date），Cookie `sid` 设 HttpOnly、Secure、SameSite=Lax，同时支撑在线用户列表。
- **Token 轨（自动登录 100 天）**：JWT（HS256，WebCrypto）载荷 `{uid, tv: token_version, iat, exp}`，存 Cookie `at`。请求进入时优先查 session；缺失则验 JWT 并重建 session。签发超过 30 分钟的 token 使用前回查用户记录核对 `token_version`。
- **改密吊销**：`user.token_version + 1` 使所有旧 JWT 失效。
- **管理轨**：管理接口额外要求 `admin_at` Cookie（gid=1 登录时签发，1 小时 TTL，每次校验续期）。

### 5.2 CSRF 与内容安全

- SameSite=Lax + 非 GET 请求双提交校验 `X-CSRF-Token`。
- 非管理员 HTML 按白名单过滤，剥离事件属性与危险协议；管理员 doctype=0 原文放行。
- `message_fmt` 在写入时生成，前端仅对 fmt 字段使用 `dangerouslySetInnerHTML`。
- **写时定稿**：sanitize 与 UBB/Markdown→HTML 解析只在写入时执行一次，读路径严禁重新解析，避免详情页 CPU 从 <2ms 升至 5–10ms。
- 附件扩展名白名单，名单外统一改名 `_ext`。

### 5.3 密码哈希

Workers 免费层 CPU 上限 10ms，Argon2id、bcrypt cost≥8、高迭代 PBKDF2 均不可用。方案：

- 主方案 WebCrypto `PBKDF2-SHA256` + 每用户 16B 随机 salt；本机实测 2 万次迭代约 2.7ms，生产取 **2 万次** 作为基线，保留 3 倍余量应对运行时波动；`PasswordHasher` 接口带 `iterations` 参数，便于复核后上调。
- 补偿控制：Turnstile、IP+账号双维度失败计数（5 次锁 15 分钟）、改密全端吊销。
- 存量兼容：按旧格式 `md5(前端md5(明文) + salt)` 校验，通过后不在登录请求内立即重哈希（避免 2× CPU 超墙），标记待升级，在改密或低频后台任务中升级。
- 升级路径：Workers 付费档 CPU 上限提升至 30s，可切换 Argon2id 并懒升级存量哈希。

### 5.4 人机验证与风控

Turnstile 覆盖登录、注册、找回密码、发码、发帖、回帖；编辑已有内容不校验。发帖/回帖的校验位于参数解析之后、任何 D1 读写之前。未配置 `TURNSTILE_SECRET` 时直通。验证码发送按邮箱 60s 限频并设每日上限。

## 6 缓存与性能设计

### 6.1 缓存分层

```
L-1  Cache API 边缘响应缓存：命中即返回，runlevel/CSRF/路由均不执行
L0   Isolate 内存 Map + TTL（10–60s）：吸收单实例热点，零额度
L1   KV（TTL 1h）：仅存极低变更的全局配置（setting/forumlist/grouplist/theme）
L2   D1 cache 表（带 expiry）：高变更共享缓存或 KV 降级层
```

### 6.2 缓存键与失效

| 缓存键 | 存放层 | TTL | 失效时机 |
|---|---|---|---|
| 游客只读响应（列表/详情/右栏聚合）、爬虫预渲染 HTML | L-1 Cache API | 列表 30s / 详情 60s / 榜单 5min–1h / 站点配置 1–10min / 爬虫页 1h | 短 TTL 到期 + 前端主动失效 |
| `forumlist`（含 access 矩阵） | L1 KV | 1h | 版块、权限、用户组变更 |
| `grouplist` | L1 KV | 1h | 用户组编辑 |
| `setting` | L1 KV | 1h | 后台保存设置 |
| `theme` | L1 KV | 1h | 后台切换主题 |
| `user:{uid}` | L0 + L2 | 30s | 资料、头像变更 |
| `runtime`（今日统计） | L0 攒批 | 10s | 计数异步合并写入 |

KV 免费层写额度仅 1000 次/天，高变更键（如 `user:{uid}`）严禁写入 KV；KV 只承载仅后台改动才写的全局键。

### 6.3 边缘缓存约束

- 缓存键只取 URL（含查询串），不认 `Vary`；爬虫与人类响应通过键参数 `?fi-ua=human/searchbot` 隔离。
- 仅在自定义域（Cloudflare Zone）生效；`*.workers.dev` 直访不生效，本地 `wrangler dev` 可验证。
- 不支持 `stale-while-revalidate` / `stale-if-error`，只用 `max-age`。
- 仅缓存匿名只读响应：带 `sid`/`at`/`admin_at` Cookie 或 `Authorization` 的请求整层绕开；带 `Set-Cookie` 的响应不缓存。
- 错误信封统一 `Cache-Control: no-store`，绝不入缓存。
- HIT 跳过整条中间件链：runlevel 调整最多延迟 30s 生效，详情浏览量按 TTL 窗口计。
- Worker 内 `cache.delete` 只清理本机柜，无网络级按 URL 失效，写后刷新依赖短 TTL 与前端失效。

### 6.4 资源预算守卫

1. 聚合接口一律 `DB.batch([...])`，一次 batch 计 1 次子请求。
2. 用户信息批量化 `WHERE uid IN (...)`，禁止 N+1；列表页依靠反规范化列免除用户查询。
3. 禁止 `SELECT *`；列表查询不触碰长文本列。
4. 深分页使用游标；`OFFSET 50000` 实测读取 5 万行，游标仅约 23 行。
5. D1 封装层维护 per-request 查询计数器，超 40 条告警。
6. CI 三预算断言：子请求 >40、mock CPU >8ms、rows_read 超上限即失败；哈希、sanitize、渲染兜底等纯计算路径单独基准测试。

## 7 文件存储

### 7.1 桶与键规划

单桶 `freeidx-files`，按前缀分区：

```
avatar/{000uid 补 9 位}/{uid}.png   # 头像
tmp/{uid}_{rand15}.{ext}            # 上传暂存（status=0）
attach/{YYYYmm}/{rand}.{ext}        # 正式附件（按年月分目录）
```

### 7.2 上传与生命周期

1. 前端上传（base64 或 multipart，业务上限 ≤20MB，图片由客户端 canvas 缩放/裁剪）→ R2 `tmp/` + `attach(status=0)`，返回 `{aid, url}`。
2. 编辑器插入图片引用 `/attachments/{aid}/preview`，按 status 控制访问。
3. 发帖/回帖携带 `attachAids[]` → 关联 pid/tid、置 `status=1`、迁移到 `attach/YYYYmm/`、回写计数。
4. 每日 Cron 清理超过 24 小时的 `status=0` 临时文件。

该流程避免正文替换与 aid 重用问题，临时文件生命周期由表驱动。

### 7.3 访问控制

附件下载校验 `allowdown` 并计数；临时件仅上传者可见；正式件由本人或版主删除。头像 ≤40KB，URL 携带 `avatar` 时间戳作缓存失效串。

## 8 前端设计

### 8.1 渲染策略

纯 SPA 无法满足百度等不执行 JS 的引擎收录要求，V1 采用**SPA + 爬虫预渲染**：

- 普通用户访问 Vite 构建的 SPA（React Router 7 data router）。
- 爬虫 UA（名单 + 特征）命中时返回**写入期生成**的语义 HTML：发帖/编辑时同步产出 title、meta、canonical、JSON-LD 与正文结构，存 R2 `seo/{tid}.html`；爬虫读路径为 Cache API → R2 get（I/O 不计 CPU），请求期 CPU 结构性归零。
- cache-miss（新帖或冷内容）用模板字符串拼装兜底，绝不在热路径执行 React SSR；渲染失败回落 SPA 壳 + 最小模板。
- 预渲染仅对白名单爬虫生效，防止伪造 UA 消耗额度。
- Phase 2（M6 可选）：全量 Hybrid SSR，入口已在 Phase 1 打通，可渐进升级。

### 8.2 路由设计

| 前端路由 | 页面 |
|---|---|
| `/`、`/page/:n` | 首页 |
| `/forum/:fid` | 版块页 |
| `/thread/:tid`、`/thread/:tid/p/:page` | 主题详情 |
| `/thread/create/:fid`、`/post/:pid/edit` | 发帖 / 编辑 |
| `/login`、`/register`、`/resetpw` | 登录 / 注册 / 找回密码 |
| `/user/:uid`（含主题/回帖 tab）、`/me` | 用户主页 / 个人中心 |
| `/mod/:fid`、`/admin/*` | 版务台 / 管理后台 |

`.htm` 旧链由 301 层收敛到新路由（如 `thread-1-1.htm → /thread/1/p/1`），用于存量站点迁移时继承收录权重。

### 8.3 外观主题体系

仅支持内置完整主题：主题是参与构建的前端代码，不支持后台上传样式包。

| 项 | 约定 |
|---|---|
| 存放 | `apps/web/src/themes/<id>/`，文件夹名即主题 id；必需 `theme.json` + `index.tsx`，可选 `theme.css` |
| 注册 | 构建期 `import.meta.glob` 自动发现，新建文件夹即完成注册 |
| 接管点 | `layout`（整站外壳）、`slots`（header/dock/footer）、`pages`（17 个前台路由整页替换） |
| 基底继承 | `light` 为基底主题，自带布局与全部前台页面；其他主题只写差异，未覆写部分自动继承 |
| 生效链路 | Worker 在 SPA 壳注入 `window.__FI_THEME__` → 缺失时读 `GET /api/theme/active` → 加载主题 CSS 与模块；任何失败回落 `light` |
| 后台管理 | `/admin/themes` 启用主题，写 kv `theme`；主题卡片按 `configPath` 进入设置页 |
| 构建门禁 | `scripts/check-themes.mjs` 校验目录仅含主题文件夹、必需文件齐全、`theme.json` 合法且 id 唯一 |

简蓝主题（`themes/light`）的外观配置仍由扩展 `light` 承载（kv `ext:light:config`），该扩展在插件中心隐藏，入口由主题管理卡片提供。

### 8.4 组件与状态

- 全局状态：`useAuth`（`/api/me`）、`forumList`（缓存 + access 过滤）、i18n provider（zh-cn 默认，前后台全覆盖）。
- 编辑器：TipTap，工具栏含图片上传、代码插入、引用回复；附件进度条；图片客户端裁剪压缩。
- 已读标记：localStorage 记录已读 tid + 列表角标，纯前端实现。
- 代码分割：前台页面按主题 `lazyPage()` 独立 chunk；后台与编辑器 chunk 不对普通访客下发。

### 8.5 管理后台

`/admin/*` 为独立外壳，不套前台布局，全部接口经 `admin_at` 校验。功能覆盖站点设置、版块与权限矩阵、用户与用户组、帖子与版务、modlog、统计、缓存清理、扩展管理、主题管理、会员/订单/积分管理、广告位管理。

## 9 后台任务与外部服务

### 9.1 定时任务

| 频率 | 任务 |
|---|---|
| 每 5 分钟 | session GC（超过 `online_hold_time` 清理）、在线数缓存刷新、队列消费 |
| 每日凌晨 | today* 统计清零、临时附件 GC、queue GC、table_day 记录、计数校准与 lastusername 自愈、SEO HTML 重建队列 |

### 9.2 异步队列

使用 D1 `queue` 表，提供 `push/pop/gc` 原语，承载计数批刷、邮件重试等异步任务；V1 由 Cron 每 5 分钟消费，不引入付费 Queues。

### 9.3 邮件服务

Workers 通过 `cloudflare:sockets` 支持出站 TCP；25 端口被封，465（隐式 TLS）/587（STARTTLS）可用。采用 **SMTP 账号池**：

- 后台配置多个账号（发件地址、服务器、端口、用户名、密码、每日限额），按 round-robin 轮询发送，单账号失败自动顺延下一个。
- 达到每日上限的账号当日跳过，次日恢复；计数存 kv `ext:email:cnt:{ymd}:{user}`，UTC 日切。
- SMTP 客户端内置于 Worker（EHLO → STARTTLS → AUTH LOGIN → MAIL FROM → RCPT TO → DATA），发送经 `waitUntil` 旁路执行，绝不阻塞请求。
- 配置存 kv `ext:email:*`，密码 AES-GCM 加密、永不回显。
- 账号池为空时自动降级为不验证邮箱，注册流程仍完整可用。

## 10 扩展机制

### 10.1 扩展模型

| 概念 | 机制 |
|---|---|
| 注入点 | 后端：Hono 中间件注册表 + 生命周期事件；前端：组件插槽 |
| 覆盖方式 | 不开放源码级文件覆盖；外观定制走主题体系，功能扩展走插件 |
| 开关 | `manifest.json` + kv `extensions` + 后台启停页 |

### 10.2 扩展点契约

V1 定义八项契约，插件只能依赖契约，不得依赖彼此：

1. 中间件注册。
2. 生命周期事件（`post:created`、`thread:deleted`、`render:*` 等）。
3. `registerRoute`：注册 Worker 路由（sitemap、llms.txt、验证文件、301 层等）。
4. `registerCron`：注册定时任务（索引推送、掉单对账等）。
5. `render:head(PageMeta)`：为预渲染 head 贡献片段，PageMeta 包含路由类型、实体数据与 setting 源。
6. `robots:contribute`：贡献 robots.txt 片段，由核心装配引擎有序合并去重。
7. `bootstrap:contribute`：向 `/api/bootstrap` 贡献字段，插件数据随核心一次下发。
8. 前端组件插槽。

官方插件：支付四插件（card/paypal/stripe/alipay）、`seo`、`geo`、`ads`。

### 10.3 插件结构

```
apps/api/src/extensions/
├── payment-core/        # 非插件：支付契约 + 注册表 + 订单状态机
├── card/                # 卡密插件（出厂启用）
├── paypal/              # 独立插件
├── stripe/
├── alipay/
├── seo/                 # sitemap/JSON-LD/OG/301/推送
├── geo/                 # llms.txt/AI 爬虫策略
└── ads/                 # 广告位 + AdSense（出厂停用）
```

每个插件 = `manifest.json` + `index.ts` + `config-schema.ts`。配置隔离在 kv 命名空间 `ext:{pluginId}:config`（非敏感）与 `ext:{pluginId}:secret`（AES-GCM 加密），插件不得读取其他插件配置。

### 10.4 与主题的边界

主题走构建期代码加载与基底继承，插件走钩子与插槽热插拔，两者不共用注册表。唯一交点是简蓝主题的外观配置由扩展 `light` 承载，该扩展在插件中心隐藏。

### 11.1 会员体系

会员体系复用 `user`/`attach` 的积分字段与 101–105 等级组，不改动组权限模型。

| 模块 | 设计 |

| 积分 | 发主题、回帖、每日首帖等获取；付费附件消费；所有变动写 `point_log`，带幂等键，禁止裸改余额 |
| 付费附件 | 上传者设置积分价格，下载时扣减；本人/版主/VIP 免扣（可配） |
| VIP | `vip_plan` 定义月/季/年计划；VIP 用户挂 gid=106，复用权限矩阵；`vip_expire_at` 到期由每小时任务降回原组 |
| 订单 | `order` 状态机 pending → paid → fulfilled/refunded；支付成功延长 VIP 或充值积分 |
| 后台 | 计划 CRUD、订单查询与补单、卡密生成、积分调整（强制理由并留流水）、VIP 列表 |

积分余额与流水必须在同一 `DB.batch()` 事务内完成；发放挂在 `post:created` 生命周期事件，与自动升组同一钩子链。掉单对账由每小时 Cron 拉取近 24 小时成功支付比对 pending 订单（卡密除外）。

### 11.2 支付插件

核心 `payment-core` 不含任何通道代码，只提供契约、注册表、订单状态机、webhook 分发与对账编排。四个通道各自独立安装/启用/停用/卸载。

契约（类型定义在 `packages/shared`）：

```ts
interface PaymentProvider {
  id: string;
  createCheckout(order, cfg): Promise<
    | { mode: 'redirect'; url: string }
    | { mode: 'qrcode'; content: string }>;
  verifyWebhook(req, cfg): Promise<ProviderEvent | null>;
  queryOrder?(ref, cfg): Promise<ProviderOrderStatus>;
  refund?(order, cfg): Promise<RefundResult>;
}
```

| 插件 | 集成方式 | 验签 | 交互 | 资质 |
|---|---|---|---|---|
| card | 核心 card 表 + 兑换码 | 无 | 输入表单 | 无，出厂启用 |
| paypal | Orders API v2 REST | webhook 证书 RSA-SHA256 | redirect | PayPal 商家账户 |
| stripe | Checkout 托管收银台 / REST | webhook HMAC-SHA256 | redirect | 海外主体 |
| alipay | 网关直连 REST + RSA2 | 异步通知 RSA2 验签（公钥模式） | 扫码 / WAP | 国内主体 + ICP |

- Webhook 入口 `/api/payments/webhook/:pluginId`，未安装 404、已停用 410；先验签后处理，`provider_ref` 唯一约束保证幂等。
- 收银台由 payment-core 聚合已启用插件，按币种、地区与 capabilities 过滤排序，随 bootstrap 下发；未启用通道自动隐藏。
- 密钥用 master key（wrangler Secret）AES-GCM 加密存各插件命名空间，更换即时生效，私钥不进响应与日志。
- 热插拔分两级：L1 配置级（v1，免费层可用，启停只改 kv）；L2 代码级（付费档 + Dynamic Workers，仅第三方通道真实需求时启用）。

### 11.3 SEO 与 GEO

**核心保底（不可停用）**：爬虫预渲染管线、语义 HTML、无登录墙、每页唯一 title/description、canonical、permalink 与楼层锚点、机器可读时间、robots.txt 装配、爬虫 UA 分类、CWV 工程配置。

**seo 插件**：sitemap.xml（分片 ≤5 万 URL、带 lastmod）、JSON-LD（WebSite/SearchAction、BreadcrumbList、DiscussionForumPosting、Comment）、OG/Twitter Card、`.htm` 301 层、IndexNow/百度推送、站点验证。

**geo 插件**：`/llms.txt`、AI 爬虫策略、精华帖对爬虫全文开放策略。AI 爬虫名单由核心统一维护（15 个 token，按"训练/检索/用户触发/robots 专用"分档）；默认允许，关闭时同时写 `Disallow` 并对页面请求返回 403，声明与执行一致。

两插件出厂启用、可独立停用：停用 seo 后核心保底仍可收录；停用 geo 后 llms.txt 404、AI 爬虫规则回落核心默认。插件间零依赖，共享产物（robots、UA 分类、站名）由核心仲裁。

### 11.4 广告系统

`ads` 为独立官方插件，出厂 `installed=1`、`enable=0`，后台可独立启停、卸载，停用后全站零广告且无占位残留。

| 项 | 设计 |
|---|---|
| 位置 | header、footer、sidebar、thread_top、thread_bottom、post_between（每 n 楼）、forum_list_between（每 n 行） |
| 类型 | `html`（仅管理员录入，走信任链）、`image`（图片 + 落地页）、`adsense`（data-ad-slot + 响应式） |
| 下发 | 经 `bootstrap:contribute` 随核心一次下发，不产生额外请求 |
| 渲染 | 前端组件插槽 `<AdSlot position>`，无数据不占位 |
| 性能 | 每位置固定 min-height 防 CLS；`adsbygoogle.js` 全站只加载一次 |
| 安全 | `ads.txt` 经 `registerRoute` 输出，发布商 ID 存 `ext:ads:secret`；爬虫预渲染不注入 AdSense |
| 合规 | 内置可选同意横幅；完整 TCF CMP 列入 M6 |

## 12 容量与演进

### 12.1 容量模型

假设 100 万内容行（10 万主题 + 90 万回帖，平均每帖 3KB）：

| 资源 | 百万内容需求 | 免费层供给 | 结论 |
|---|---|---|---|
| D1 存储 | 数据 + 索引约 4–6GB | 单库 500MB | 首个硬墙，必须升级或归档 |
| D1 读 | 详情 miss 约 40–60 行；列表页单表约 30 行；匿名走边缘缓存零读 | 500 万行/天 | 缓存命中后约 8–12 万次详情 miss/天 |
| Workers 请求 | SPA 每 PV 约 4–8 次 API（bootstrap 聚合后）；边缘命中仍计一次请求 | 10 万/天 | 约 1.5–2.5 万 PV/天 |
| R2 | 图片为主，10GB 约 2–5 万张 | 10GB，无出站费 | 基本满足，可按需清理 |
| CPU | 稳态读 <2ms | 10ms/请求 | 满足（写时定稿、哈希留余量、写入期预渲染） |

**结论**：免费层可支撑约 30 万内容行、1 万 PV/天的论坛稳定运行；"百万内容 + 常态访问"需升级付费档，但架构无需推翻。

### 12.2 演进路径

| 档位 | 适用规模 | 方案 | 月成本 |
|---|---|---|---|
| P0 免费层 | ≤30 万行、≤1 万 PV/天 | 本设计默认形态 | $0 |
| P1 Workers Paid | 100–500 万行、≤10 万 PV/天 | CPU 上限 30s、请求按量、D1 10GB/库 + 读副本、可切 Argon2id | $5–15 |
| P2 冷热分层 | >500 万行或逼近 10GB | 热数据留 D1，冷帖正文归档 R2 JSON，详情 miss 走 R2 + 长缓存 | +$1–5 |
| P3 极端规模 | 更大规模 | 按版块分库或外置 serverless Postgres，非必要不采用 | — |

### 12.3 V1 内置优化

1. 游客只读接口与爬虫页走 Cache API，命中对 D1 零读取。
2. 聚合接口 + `DB.batch()`，bootstrap 一次下发版块/用户/插件字段。
3. `thread` 反规范化用户快照，列表页零 JOIN、零二次查询。
4. 详情页 `max-age=60`，写后即时刷新由前端缓存失效承担。
5. 浏览量、回帖计数在 Isolate 内攒批后合并写库。
6. 深分页使用游标 + ">100 页倒排"，杜绝深 OFFSET。
7. 列表覆盖索引，禁止 `SELECT *` 与长文本列读取。
8. 附件本体不进 D1；搜索预留 FTS5（M6 启用）。

## 13 部署与工程化

### 13.1 运行时配置

`apps/api/wrangler.toml` 要点：

```toml
name = "freeidx-api"
main = "src/index.ts"
compatibility_date = "2026-10-01"

[[d1_databases]]
binding = "DB"
database_name = "freeidx"
database_id = "…"

[[kv_namespaces]]
binding = "CACHE"
# 命名空间名 freeidx-cache，CI 自动创建/复用
id = "…"

[[r2_buckets]]
binding = "FILES"
bucket_name = "freeidx-files"

[triggers]
# 表达式唯一事实源：apps/api/src/core/cron-schedule.ts（每日档 03:01，错开 03:00 的 */5 与每小时档）
crons = ["*/5 * * * *", "0 * * * *", "1 3 * * *"]

[vars]
SITE_URL = "https://example.com"
# JWT 密钥、Turnstile secret 等经 wrangler secret put 注入，不进仓库
```

Pages 项目绑定 `apps/web`，构建命令 `pnpm --filter web build`。

### 13.2 域名与路由

推荐同域部署（自定义域）：

- `/`、`/assets/*` → Pages
- `/api/*`、`/files/*` → Worker（Zone Routes）
- 使用 `api.` 子域需额外配置 CORS 与 SameSite=None，不推荐。

### 13.3 安装与迁移

1. `wrangler d1 create freeidx` → `wrangler d1 migrations apply` 建表。
2. `pnpm seed` 写入预置用户组、默认版块、forum_access 矩阵，并创建首个管理员。
3. `wrangler secret put` 注入 JWT 密钥、Turnstile secret；SMTP 凭据走后台加密 kv。
4. 存量导入由迁移工具读取旧站 MySQL dump，生成 D1 INSERT；密码不明文迁移，沿用 md5 兼容链路；存量 `message_fmt` 直接沿用；附件按旧目录批量上传 R2 并回填 key；最后批量生成 SEO HTML。

### 13.4 CI/CD

- PR：类型检查 + 单测（权限引擎、message_fmt 快照为重点）+ D1 migration dry-run + 三预算断言。
- main：构建 Pages 预览与 Worker 预览。
- 生产：手动门禁执行 `wrangler deploy --env prod`。
- 生产发布所需 Secrets/Variables、总开关与首次上线步骤见 [部署与发布](部署与发布.md)。

### 13.5 可观测性

`wrangler tail` 排障 + 后台 runtime 统计页（今日帖子、在线数、子请求/CPU/rows_read 监控）+ D1 查询耗时打点。每阶段收尾记录 D1 读写行数、Workers 请求数、KV 写次数与 R2 用量，作为额度基线。

## 14 实施计划

### 14.1 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M0 骨架 | monorepo、脚手架、全表迁移、seed、CI、三项实测（PBKDF2 迭代数、Cache API + R2 延迟、D1 batch/行读上限） | 两端部署成功；健康检查通过；实测值写回文档 |
| M1 只读闭环 + SEO 基座 | 权限引擎、三层缓存、读接口、只读页面、i18n、扩展点契约、seo 插件一期 | 游客全流程可用；三大引擎抓取可见完整语义 HTML；停用 seo 后核心仍可收录 |
| M2 写路径 | 注册/登录/双轨鉴权、Turnstile、富文本发帖回帖、附件 R2 全流程、头像、自动升组、SEO HTML 生成侧 | 登录用户全流程可用；读路径 CPU <2ms |
| M3 版务后台 + 广告 | 批量版务 + modlog、admin 全模块、runlevel、Cron/队列、ads 插件 | 管理员可运营站点；广告可独立启停 |
| M4 长尾 + GEO | 找回密码与邮件、我的回帖、在线列表、统计、数据迁移、压测校准、geo 插件与 seo 二期 | 功能清单全绿；GEO 检查通过；插件互不影响 |
| M5 会员与支付 | 积分账本、付费附件、VIP/订单、payment-core、card 与三条外部通道 | 购买→支付→回调→开通闭环；通道独立热启停 |
| M6（可选） | 全量 SSR、FTS5 搜索、冷热归档、L2 代码级热插拔、完整 TCF CMP | 按需触发 |

### 14.2 实施原则

1. **表结构一次定稿**：全表、全索引、seed 同批完成，避免上线后加列回填与双写。
2. **权限引擎先于业务接口**：`core/access.ts` 与 runlevel 是第一个可测模块，作为后续所有接口的闸口。
3. **预算守卫与 D1 封装同批落地**：查询计数器、CI 断言、batch 助手、游标分页原语、显式投影约定先行。
4. **写时定稿先于读路径上线**：sanitize、格式转换、SEO HTML 生成全部归写接口。
5. **契约先冻结**：共享类型、扩展点契约、DTO 冻结后，前端可 mock 并行；插件只能复用契约，不改签名。
6. **实测项前置**：三项 spike 在 M0 完成并回写参数；外部依赖（Turnstile、邮件账号、支付资质、域名）并行申请，不阻塞编码。

### 14.3 阶段门禁

| 门禁 | 时点 | 通过条件 |
|---|---|---|
| G1 数据模型冻结 | M0 末 | `0001_init` 覆盖全部表/列/索引，含业务表与反规范化列 |
| G2 契约冻结 | M1 末 | 八项扩展点契约有类型与单测；seo 插件作为首个消费者跑通；DTO 冻结 |
| G3 写时定稿确立 | M2 末 | 读路径 CPU 实测 <2ms；sanitize/fmt/SEO 全在写侧；快照测试入 CI |
| G4 收录验收 | M1 末与 M2 末各一次 | 三大引擎抓取可见完整语义 HTML |
| G5 支付范围决策 | M4 末 | 支付资质、广告默认策略、容量档位均有结论；否则 M5 仅交付账本与卡密 |

### 14.4 明确不实施项

| 项 | 原因 |
|---|---|
| 禁言强制逻辑（ban/allowbanuser） | V1 仅保留字段，后续以扩展补齐 |
| IE 降级页、Web 安装向导、后台自检页 | 目标为现代浏览器；Workers 部署即安装 |
| 历史版本升级脚本 | 存量导入走迁移工具 |
| 搜索/标签/第三方登录 | 非 V1 范围，搜索列入 M6 |
| 源码级文件覆盖 | 破坏可维护性，外观定制走主题体系 |
| L2 代码级热插拔 | 需付费档与真实第三方通道需求，L1 已满足 V1 |
| `table_day` 冷热过滤 | 建表不启用，归档属 P2/M6 |

## 15 风险与决策记录

### 15.1 主要风险与对策

| 风险 | 对策 |
|---|---|
| D1 写入额度与 500MB 单库上限 | 计数攒批、异步合并；runtime 页监控写行量；内容逼近 30 万行启动 P1 |
| 单请求 50 条查询上限 | `DB.batch()` 聚合 + 查询计数器 + CI 预算断言 |
| Workers 10 万请求/天 | 聚合接口一次下发、图片直链走缓存、bootstrap 合并插件字段 |
| CPU 10ms 硬上限 | 密码哈希低迭代留余量；爬虫渲染移至写入期；sanitize 写时定稿；CI 三预算断言 |
| 支付回调可靠性 | 验签 + `provider_ref` 唯一约束幂等 + 每小时掉单对账 |
| 边缘缓存陈旧 | 短 TTL + 前端主动失效；已删主题对爬虫最多 1h 残留，知情接受 |
| 免费层密码哈希强度不足 | Turnstile + 失败锁定 + 改密吊销组合补偿；付费档可升 Argon2id |

### 15.2 关键决策记录

| 决策项 | 结论 |
|---|---|
| 渲染策略 | V1 采用 SPA + 写入期预渲染；请求期不执行 React SSR；全量 SSR 延后 M6 |
| 密码哈希 | PBKDF2-SHA256 生产基线 2 万次迭代；登录请求内不做重哈希 |
| 富文本编辑器 | TipTap（ProseMirror） |
| 邮件通道 | `cloudflare:sockets` SMTP 账号池，轮询 + failover + 每日限额 |
| URL 兼容 | 保留 `.htm` 301 层，继承存量收录权重 |
| 人机验证 | Turnstile 替代图形验证码 |
| 支付通道 | 卡密必做，PayPal/Stripe/支付宝各自独立插件，按资质逐个启用 |
| 广告默认策略 | ads 插件出厂停用，管理员启用后投放 |
| AI 爬虫策略 | 默认允许，后台可关闭；关闭时声明与执行同时生效 |
| SEO/GEO 拆分 | 核心收录保底不可停用；seo/geo 两插件出厂启用、可独立停用 |
| 容量路径 | 免费层起步，超 30 万行或 PV 超限后升级 P1 |

### 15.3 遗留事项

| 项 | 现状 | 处理建议 |
|---|---|---|
| 重复 checkout 静默、退款不回收 VIP 权益 | 已知，暂缓 | 后续版本评估 |
| AdSense 发布商账号与 ads.txt | 待运营配置 | 启用 ads 插件前完成 |
| GDPR 地区完整 TCF CMP | 当前为简单同意横幅 | M6 可选升级 |
| 支付通道资质 | 取决于站点主体 | M5 前确认通道范围 |
| SEO 已删主题对爬虫的 ≤1h 残留 | Cache API 技术限制 | 接受，纳入监控 |
