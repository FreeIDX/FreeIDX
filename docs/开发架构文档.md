# FreeIDX 架构设计 —— Cloudflare 平台全栈方案

> 目标：FreeIDX 论坛全站运行于 Cloudflare 免费层——**React 19 + Tailwind CSS 4 前端（Cloudflare Pages）** + **TypeScript Worker 后端（Cloudflare Workers 免费层）**，数据层 D1/KV/R2，零服务器运维成本。

> 状态：设计稿 v3.2（已全面核对修正；v3 新增会员体系/SEO+GEO/广告系统/容量评估；v3.2 §14 扩充为"路线图 + 执行开发计划"：工单级开发顺序、并行轨道、阶段门禁）

明确**不做**的部分：
- IE 降级提示页——目标浏览器即现代浏览器，无意义。
- 跨站单点登录（依赖私有加密格式）——如后续需要，用标准 OAuth/JWT 重做，不阻塞 v1。
- 外部插件市场对接——不依赖第三方市场，保留本地扩展机制即可。
- 长尾扩展（搜索、标签、第三方登录、公众号、多主题等）——不在 v1 范围，但 §12 扩展点保证其可被重写；其中搜索建议 M4 后以 D1 `LIKE` 简版补上。
- 历史数据升级脚本——仅服务于旧版本迁移，不搬移；数据导入用 §13.3 迁移工具。
- Web 安装向导——改为 wrangler 迁移 + seed 创建首个管理员（见 §13.3）；传统自检信息页无对应物，弃用。

### 1.2 平台约束（Cloudflare 免费层）

> 额度以 [官方定价页](https://developers.cloudflare.com/workers/platform/pricing/) 最新数据为准，设计按以下假设留有余量。

| 服务 | 免费额度（参考） | 对本设计的影响 |
|------|------------------|----------------|
| Workers | 10 万请求/天；**CPU 硬上限 10ms/请求（免费层不可上调**，wall clock 50s；付费层才可配 cpu_ms 至 30s+）；请求体上限 100MB（账户级） | API 必须轻量；重计算放 `waitUntil`（不占响应 CPU 预算的路径有限，注意 waitUntil 同样受 CPU 限制约束）；**密码哈希迭代数必须压进 10ms**（见 §8.4） |
| Pages | 请求/带宽不限，每月 500 次构建 | 前端托管无忧 |
| D1 | **单库 500MB**（账户 5GB / 最多 10 库）、500 万行读取/天、10 万行写入/天、**单次 Worker 调用最多 50 条 D1 查询**、单行/单列最大 2MB、单条 SQL ≤100KB | 核心库。**写放大与 50 查询/请求是两大风险** → 高频读走缓存；多表聚合必须用 `DB.batch()` 合并；计数更新用 `waitUntil` 异步合并 |
| KV | 10 万读/天、1 万写/天 | 只做**低频写、高频读**的缓存层（forumlist、grouplist、setting），绝不用来存 session |
| R2 | 10GB 存储、A 类 100 万/月、B 类 1000 万/月、**无出站流量费** | 附件/头像存储，免费层中最划算的存储 |
| Cron Triggers | 免费 | 承担定时任务 |
| Queues | 需付费计划 | **不用**，采用数据库队列表思路（D1 queue 表） |

### 1.3 架构原则

1. **免费层优先**：所有选型零成本；超限时给出付费升级路径但不依赖。
2. **功能完整 > 架构新颖**：权限模型、响应信封、URL 语义保持稳定约定，避免"上线即改版"。
3. **无服务器状态**：Worker 无本地磁盘、无进程常驻；session/文件/统计全部落 D1/R2。
4. **写路径最短，读路径有缓存**：D1 写入额度是稀缺资源。
5. **前后端契约先行**：`packages/shared` 定义类型与错误码，两端共用。

## 2. 总体架构

```
                        ┌──────────────────────────────┐
   浏览器（现代设备）      │   Cloudflare CDN 边缘         │
        │               └──────────────┬───────────────┘
        │ 页面/静态资源                  │ /api/* 转发（或前端直连 api 域名）
        ▼                              ▼
┌──────────────────────┐   ┌────────────────────────────────┐
│  Cloudflare Pages     │   │  Cloudflare Worker「freeidx-api」│
│  React 19 + Tailwind 4│   │  Hono (TypeScript)              │
│  SPA（首阶段）         │◄──┤  ├ 鉴权中间件（JWT+Session 双轨）  │
│  管理后台路由 /admin/* │JSON│  ├ 权限引擎（组×版块×版主）        │
└──────────────────────┘   │  ├ 业务路由 forum/thread/post/…  │
        ▲                  │  └ Cron Trigger（5min/每日任务）  │
        │ 图片/附件直链       └───────┬────────┬────────┬───────┘
        │                            │        │        │
┌───────┴────────┐          ┌────────▼──┐ ┌───▼────┐ ┌─▼──────────┐
│ Cloudflare R2   │          │ D1         │ │ KV     │ │ 外部邮件 API │
│ /attach /avatar │          │ 核心数据+   │ │ 缓存层  │ │ (Email     │
│ /tmp 桶前缀      │          │ session+kv│ │(低频写) │ │  Provider) │
└────────────────┘          └───────────┘ └────────┘ └────────────┘
```

要点：
- **Pages 只负责前端**；数据全部经 `fetch` 调 Worker API（CORS 白名单或同域根路径反代）。
- **图片/附件由 Worker 流式代理 R2**（`GET /files/:key`），加 Cache API/浏览器强缓存，规避 R2 B 类操作额度并享受零出站费。
- **同域部署推荐**：自定义域下 `/` → Pages、`/api` `/files` → Worker（Routes 配置），省掉 CORS 且 Cookie 天然同域。

## 3. 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 前端框架 | **React 19** + **React Router 7（data router）** | 用户指定；RR7 的 loader/action 模式天然贴合论坛数据流 |
| 样式 | **Tailwind CSS 4**（CSS-first 配置） | 用户指定；4.x 无需 tailwind.config.js，配 `@theme` 定制主题色 |
| 数据请求 | TanStack Query | 列表/详情缓存、乐观更新（发帖数、浏览量）、无限滚动 |
| 客户端状态 | Zustand（登录用户、版块列表等全局少量状态） | 轻量 |
| 构建 | Vite 7 + TypeScript 5 | 标准 |
| 富文本/发帖 | **TipTap（ProseMirror）** 富文本编辑器；doctype=0(HTML，白名单 sanitize) 为主通道，1(txt)/2(md) 兼容渲染；3(ubb) 仅存量展示 | 免维护、Workers 友好；工具栏含代码插入（插入代码扩展 idx_insert_code）与图片上传 |
| 后端框架 | **Hono** | Workers 生态事实标准，路由中间件体积极小，满足 10ms CPU |
| 校验 | Zod | 表单校验统一走 schema |
| 人机验证 | **Cloudflare Turnstile**（免费） | 挂载点：登录/注册/发帖/回帖/找回密码/发码（附录 B） |
| 数据库 | **D1**（SQLite） | 免费、零运维 |
| 对象存储 | **R2** | 免出站流量 |
| 缓存 | KV + Isolate 内存 LRU + D1 cache 表 + **Cache API 边缘缓存** | 三层数据缓存 + 一层响应缓存，见 §7 |
| 鉴权 | **JWT（httpOnly Cookie）+ D1 session 表双轨** | 自动登录与会话并存，见 §8 |
| 密码哈希 | **PBKDF2-SHA256（WebCrypto，迭代数受 10ms CPU 预算约束）**，兼容旧 md5+salt 懒升级 | 见 §8.4，免费层无法使用 Argon2id/bcrypt 高成本参数 |
| 计划任务 | Cron Triggers（`5 * * * *` + `0 3 * * *`） | 5min/每日两档 |
| 爬虫渲染 | **写入期预生成 SEO HTML 存 R2 + Cache API**（仅爬虫 UA 读取），请求期不跑 React SSR；cache-miss 用模板串兜底 | 收录硬需求（§16.1），把渲染 CPU 移出热路径 → 请求期 CPU 结构性归零 |
| 支付 | **每通道一个独立插件**（card / paypal / stripe / alipay），payment-core 只含契约+注册表+订单状态机；后台逐个热插拔（启停/换密钥零部署）；付费档可选 Dynamic Workers 代码级热插拔 | 会员体系（§15.5） |
| 包管理 | pnpm workspace（monorepo） | 前后端共享类型 |

## 5. 数据层设计（D1）

### 5.1 表结构约定

核心数据模型共 17 张表，语义保持论坛领域通用约定。D1/SQLite 落地约定：

| 语义 | D1/SQLite 落地 | 说明 |
|-------|-----------|------|
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | tid/pid/uid… |
| 布尔位 | `INTEGER` (0/1) | allow* 权限位、closed |
| 短字符串 | `TEXT` | |
| 时间 | `INTEGER` unix 秒 | **统一用 INTEGER unix 秒**，避免时区/解析开销 |
| 长文本 | `TEXT` | message、message_fmt、kv.v |
| 表前缀 `bbs_` | 保留 | 与常见论坛数据模型命名对齐，便于对照与迁移 |
| 索引 | `CREATE INDEX` 独立语句 | |
| `LIKE '%x%'` 分页 | D1 支持 | 深分页用**游标式** `?before_tid=`（OFFSET 跳过行仍计 rows_read，实测 OFFSET 50000 读 5 万行 vs 游标 ~23 行）+ ">100 页倒排"（§7/§18.3） |

### 5.2 表清单与关键调整

| 表 | 说明与调整 |
|----|----------|
| `user` | `password` 存新格式 `argon2id$…`；保留 `salt` 列以校验遗留 md5 哈希（懒升级，§8.4）；新增 `token_version`（改密吊销 JWT） |
| `group` | 12 个 allow* 权限位，字段语义固定 |
| `forum` | `moduids` 保持逗号串 |
| `forum_access` | (fid,gid) 复合主键 |
| `thread` | 含 top/closed/firstpid/lastpid；**新增 `digest` 列**（精华标记，0 普通 /1-3 精华级别，语义仿 top）；**新增 `username` + `lastusername`（+ `avatar` 时间戳）反规范化列**——若只存 uid/lastuid，列表页显示作者名/最后回复人需 JOIN user 或 `WHERE uid IN(...)` 二次查（每屏多读 ~30-60 行 user）；反规范化后列表页 = **单表扫描、零 JOIN、零 user 查询**，D1 rows_read 直接砍半（§7 读预算）。代价：改用户名时 `waitUntil` 异步批量回写该用户所有 thread（`username WHERE uid=?` + `lastusername WHERE lastuid=?`，带 `<> 新值`守卫，已落地 admin/users.ts backfillUsername；改名极低频，读多写少场景标准取舍；cronDaily 校准批含 lastusername 自愈语句兜底）。**lastusername 维护规则（§20.2 结构性修复）**：回帖/过审补列/删帖尾列回退三处必须与 lastpid/lastuid/last_date 同步写入（回帖用回帖者当前用户名，回退用标量子查询取新尾作者当前用户名），否则"最后回复 by X"恒显示楼主名。头像 URL 由 `avatar` 时间戳拼 R2 key，免读 user |
| `thread_top` | 置顶倒排 |
| `post` | `message` 原文 + `message_fmt`（写入时预格式化，读帖免渲染开销） |
| `attach` | `filename` 改存 **R2 object key**；新增 `status`（0=临时待关联 / 1=已入库） |
| `mythread` / `mypost` | 倒排索引；mypost 由发帖事件钩子维护（发帖时写入），"我的回帖"列表依赖它 |
| `session` | 合并 session_data：`data TEXT`（D1 单行最大 2MB，无需溢出表）；列 sid/uid/fid/url/ip/useragent/last_date 保留 → 支撑在线用户功能 |
| `modlog` | 版务审计日志 |
| `kv` | **站点设置的唯一存储**（见 §5.3） |
| `cache` | KV 未满位时的 D1 兜底缓存层 |
| `queue` | 异步任务队列表 |
| `table_day` | 按日统计辅助表（冷热过滤辅助，v1 可先建表不启用） |

新增业务表（会员体系与广告系统）：`vip_plan` / `order` / `point_log` / `card`（会员体系，§15.2）、`ad_slot`（广告位，schema 归核心、数据归 `ads` 插件独占，§17.1），随 0001_init 一并建表。

### 5.3 配置存储（重要差异点）

Workers 无文件系统，站点设置**不落配置文件**：

- 静态部署配置（D1/KV/R2 绑定、auth_key 等）→ `wrangler.toml` vars / Secrets。
- 动态站点设置（sitename、runlevel、user_create_on、forum 排序开关等 `setting_*` 键）→ `kv` 表 `setting` 键 + JSON 值，`setting_get/setting_set` API，写后失效 KV 缓存。

### 6.3 单一事实源：权限引擎

`core/access.ts` 是权限的**单一事实源**，承载全部三层判定语义，**所有**读写接口经它判定：

```
普通操作 forumAccessUser(fid, gid, 'allowread|allowthread|allowpost|allowattach|allowdown')
  forum.accesson == 0 → 只看 group.allow*
  forum.accesson == 1 → group.allow* && forum_access[fid][gid].allow*（双与）

版务操作 forumAccessMod(fid, gid, uid, 'allowtop|allowmove|allowupdate|allowdelete')
  gid==1 || gid==2 → 直接通过
  gid==3/4/5 → group.allow* && uid ∈ forum.moduids

作者叠加：allowupdate/allowdelete = (当前uid == 帖子uid && 组允许) || forumAccessMod(...)
全局闸门：runlevel（0 正常…5 仅管理员），未登录跳登录
```

单元数据/列表返回前执行三级过滤：`forumListAccessFilter` / `threadListAccessFilter` / `postListAccessFilter`（置顶帖不过滤等细节由引擎统一处理）。

**用户组自动升级**：发帖/回帖成功后，若用户 `gid >= 100`（等级组），按 `posts + threads` 总和落入各等级组 `creditsfrom/creditsto` 区间自动换组；换组即时生效于后续权限判定，并失效 `user:{uid}` 缓存。此逻辑挂在 post 创建的事件钩子上（§12 扩展点之一）。

## 7. 缓存设计（三层数据缓存 + 一层边缘响应缓存）

缓存分层：

```
L-1 Cache API（caches.default）边缘响应缓存——命中即在 Worker 内直接返回，runlevel/csrf/路由全不执行
L0  Isolate 内存 Map+TTL（10~60s）—— 吸收单实例热点，零成本、无额度
L1  KV（TTL 1h）—— **仅放极低变更的全局配置**（setting/forumlist/grouplist，只在后台改动时写）；KV 免费写额度仅 1k/天，高变更键严禁入 KV
L2  D1（cache 表，带 expiry）—— 高变更/共享缓存落此（用户态等），或 KV 写额度超限时的降级层
```

| 缓存键 | 存放层 | TTL | 失效时机 |
|--------|--------|-----|----------|
| 游客只读接口响应 + 爬虫预渲染 HTML | **L-1 Cache API** | 列表 30s / 详情 60s / 爬虫页 1h | 无网络级主动失效（Workers 内 `cache.delete` 只清本机柜）→ TTL 到期 + 前端 TanStack Query 失效 |
| `forumlist`（含 access 矩阵） | L1 KV | 1h | 版块/权限/用户组变更主动失效 |
| `grouplist` | L1 KV | 1h | 用户组编辑失效 |
| `setting` | L1 KV | 1h | 后台保存失效 |

| `user:{uid}` | **L0 + L2**（高变更，禁 KV） | 30s | 资料/头像变更失效 |
| `runtime`（今日统计） | L0 攒批 | 10s | **统计类写合并**：发帖计数在请求内攒批、`waitUntil` 每 N 秒刷一次，控制 D1 写入额度 |

> **为何高变更键禁入 KV（核实）**：KV 免费层写额度仅 **1k 次/天**（读 10 万/天）。`user:{uid}` 等高频失效键 → 每次 miss 都写 KV → 数千次访问即耗尽写额度，之后全部穿透到 D1 反而**增加** rows_read。故 KV 只承载 setting/forumlist/grouplist 这类仅后台改动才写的键；高变更键走 L0（免费无额度）+ L2 D1 cache 表。（置顶列表已改直查 `bbs_thread_top` 表，`thread_top_list` 缓存键随该方案移除，§20.3 批次 3D。）

**读取屏障（匿名/爬虫流量对 D1 零读取）——已落地为 `core/cache/edge.ts`**：匿名游客 + 爬虫是绝大多数流量且无需按用户过滤权限，其**列表页与详情页响应走 Cache API 边缘缓存**，命中即对 D1 零 rows_read（runlevel 的 kv 读取也一并省掉）。仅登录用户（需权限过滤）与 cache-miss 才落 D1。这是首要的 D1 读取削减手段，优先于一切查询级优化。

核实后的实现约束（每条都对应一次文档纠错）：

| 约束（已核实） | 实现取向 |
|---|---|
| 缓存键只取 URL（含查询串），**不认 `Vary`** | UA 分类写进键参数 `?fi-ua=human/searchbot`，爬虫 HTML 与人类响应永不互串 |
| **仅自定义域（走 Cloudflare zone）真正生效**；`*.workers.dev` 直访与 dashboard/Playground 预览为 no-op | 绑域前该层恒 miss、零副作用；绑域即自动生效，无需改代码（绑域见部署文档）。**例外：本地 `wrangler dev` 的 miniflare 自己实现了 Cache API，实测 HIT 有效**（S2 spike 即在本地跑的），所以本层逻辑不必等绑域就能验证；生产仍按不生效对待 |
| `stale-while-revalidate` / `stale-if-error` 对 `cache.match`/`cache.put` **不支持** | 原设想的"详情 SWR 60s"作废，只用 `max-age`——TTL 即最大陈旧窗口 |
| 写缓存依赖响应 `Cache-Control`（无指令/`no-store` 会被拒，`put` 返 413） | 下发给客户端的响应不带缓存头，**只在写缓存副本上打** `public, max-age=TTL`；TTL：列表 30s、详情 60s、爬虫页 1h |
| 业务错误是 HTTP 200 + `code<0`（§6.1 信封），且 Hono 会在链路内把抛出的 `AppError` 转成响应（中间件 `await next()` 之后仍能拿到） | 靠异常传播防不住污染 → `envelope.ts` 的 `fail`/`handleError` 统一打 `Cache-Control: no-store`，写入门槛据此拒绝（错误信封绝不入缓存） |
| 带 `Set-Cookie` 的响应不缓存 | 首访（无 `csrf` Cookie）必然穿透并签发 Cookie；参与资格再要求"已持有 `csrf` Cookie"，HIT 永远不会吞掉 Cookie 签发 |
| 登录态在 Cookie（`sid`/`at`/`admin_at`）里 | 出现任一即整层绕开；带 `Authorization` 同样绕开 |
| 命中仍计一次 Worker 请求（请求额度不省，省的是 CPU + D1/KV/R2 子请求与行读） | §18.1 的 Workers 请求口径不变 |
| Workers 内 `cache.delete` **只清本机柜**，无网络级按 URL 失效 | 写后刷新靠短 TTL + 前端 TanStack Query 主动失效（原设想"按 URL 主动失效"不成立） |
| HIT 跳过整条中间件链 | 后台改 runlevel 后游客最多 30s 才生效；详情页 `views` 自增在 HIT 期不累加（浏览量口径退化为"每 TTL 窗口每机柜至多一次"） |

**未采纳：wrangler `[cache]`（2026-07 起的 Workers Cache，响应在 Worker 之前被拦截、命中不计 CPU）**。它同样按 URL + `Vary` 分键而**看不见 Cookie**，本项目"同一 URL 对爬虫返回预渲染 HTML、对人类返回 SPA 壳"以及"登录态由 Cookie 决定"这两点都会被互串，且 HIT 无法完成 `csrf` Cookie 签发；故边缘缓存放在 Worker 内部（可判 Cookie），而不是放在 Worker 前面。

**S2 spike 回填（本地 workerd `wrangler dev` 实测，2026-10-07）**：`GET /api/threads` 首访 `x-edge-cache: MISS`（响应不带 `cache-control`）→ 再访 `HIT` 且带 `cache-control: public, max-age=30`，HIT 请求全程 3~4ms、D1 零查询；带 `sid` Cookie 的请求无标记并正常走全链路；`/api/threads/999999` 响应带 `no-store` 且未入缓存；Googlebot UA 请求 `/thread/1` 第二次为 `HIT`，同 URL 换人类 UA 仍返回 SPA 壳（键未互串）。单测另覆盖 HIT 零 SQL、TTL 只加在缓存副本、无 Cache API 时优雅降级（`test/edge-cache.test.ts`）。**生产边缘延迟与命中率未测**——需绑自定义域后按部署文档步骤 6 的命令复测回填本行。

**三预算守卫（免费层单次调用 ≤50 子请求、≤10ms CPU，账户级 ≤5M rows_read/天）**：
- 聚合接口（如主题详情 = thread + posts + attach + users + forum + 权限矩阵）一律用 `DB.batch([...])` 单往返并行执行，一次 batch 计 1 次 subrequest。
- 用户信息批量化：列表页收集 uid 集合后 `WHERE uid IN (...)` 一次取回，禁止 N+1；thread 已反规范化 username/lastusername（§5.2），列表页连这次 IN 查询都省掉。
- **禁止 `SELECT *`**：显式投影所需列，列表查询绝不触碰 `message`/`message_fmt` 两个 longtext 宽列（仅详情页按 pid 读取）。
- **深分页用游标不用 OFFSET（核实）**：D1 的 OFFSET 跳过行**仍计入 rows_read**——实测 `LIMIT 20 OFFSET 50000` 读 50,020 行，游标式 `WHERE tid < ?` 仅读 ~23 行。故深分页一律 `?before_tid=` 游标，杜绝 `OFFSET 100000` 类全扫（§18.3）。
- forumlist/grouplist/setting 命中 L0/L1 缓存时不产生 D1 查询。
- 开发期在 D1 封装层加 per-request 查询计数器，超 40 条告警（单测断言），防止免费层静默失败。
- **CI 三预算断言**：把查询计数器扩成"子请求 + CPU 估算 + rows_read 估算"三守卫，热路径单测跑超阈值（子请求 >40 / mock CPU >8ms / rows_read 超设定上限）直接失败，防回归。纯计算路径（哈希、渲染兜底、sanitize）单独基准测试。
- **CPU 归零原则**：读路径不做重计算——sanitize/UBB→HTML 只在写时定稿存 `message_fmt`（§8.3），爬虫 HTML 写入期预生成存 R2（§16.1），读请求只剩 JWT 验证(HMAC) + JSON 序列化，稳态 <2ms。

## 8. 认证与安全

### 8.1 双轨会话（Session + Token）

- **Session 轨**：登录后写 D1 `session` 行（sid, uid, ip, url, useragent, last_date）——同时支撑"在线用户"功能。Cookie `sid=…; HttpOnly; Secure; SameSite=Lax`。
- **Token 轨（自动登录，100 天）**：`JWT(HS256, WebCrypto)` 载荷 `{uid, tv: token_version, iat, exp}`，存 Cookie `at=…`（TTL 100 天 = 8640000s）。请求进入时：session 命中 → 用 session；否则验 JWT → 重建 session。签发超过 30 分钟的 token 使用时回查用户记录核对 `token_version`（防止改密后旧 token 长期有效）。
- **改密吊销**：`user.token_version+1` 使所有旧 JWT 失效。
- **admin 轨**：管理接口额外要求 `admin_at` cookie（gid=1 登录时签发、1h TTL、每次校验续期）。

### 8.2 CSRF

SameSite=Lax + 非 GET 请求校验 `X-CSRF-Token`（与 `csrf` cookie 双提交一致）。

### 8.3 XSS / 内容安全

- 非管理员 HTML 按白名单过滤（保留安全的标签集合，剥离事件属性/危险协议）。
- 管理员 doctype=0 原文放行（管理员信任链）。
- `message_fmt` 入库前生成，前端 `dangerouslySetInnerHTML` 仅用于 fmt 字段。
- **写时定稿硬规则（CPU 护栏）**：sanitize 与 UBB/MD→HTML 解析**只在写入时执行一次**、结果存 `message_fmt`；**读路径严禁重新 sanitize/解析**（否则高频详情页读会从 <2ms 涨到 5-10ms，把最安全的读路径拖下 10ms 墙）。`message`(原文)/`message_fmt`(渲染后) 双字段模式。
- 附件扩展名白名单；名单外改名 `_ext`（防执行策略）。

### 8.4 密码哈希升级（兼容存量，受 10ms CPU 硬约束）

**免费层约束**：Workers 免费计划 CPU 上限固定 10ms/请求，常规参数的高强度哈希（Argon2id、bcrypt cost≥8、PBKDF2 600k 迭代 ≈ 200~500ms CPU）全部超限，登录/注册会直接失败（error 1102）。方案：

- **主方案**：WebCrypto `PBKDF2-SHA256`，迭代数取 **CPU 预算内最大值并留 20% 余量（目标 ≤8ms 而非贴 10ms，应对硬件波动）**（M2 阶段实测标定；按 workerd 历史基准 10 万次 ≈50ms 反推，免费层单次登录全预算约 **1~2 万迭代**，勿沿用旧稿"5 万"——旧硬件下 5 万 ≈25ms 会超墙）。**【S1 spike 实测回写 2026-10-06】** 本机 V8（Node 24，与 workerd 同引擎）中位数标定：2 万次 ≈2.7ms、5 万次 ≈7.0ms、6.4 万次 ≈7.8ms（≤8ms 上限）、10 万次 ≈13.3ms（超限）；本机可容纳 ≈6.4 万迭代，但 workerd 计费 CPU 更快/更慢方向未知，**生产取保守值 2 万次**（≈2.7ms@本机，3 倍余量抗硬件波动），部署后以 `wrangler dev` + 远端登录实测复核后再上调；**PasswordHasher 接口含 iterations 参数**，升级迭代数走懒升级不动业务代码。+ 每用户随机 salt（16B）。低于 OWASP 推荐值，属免费层已知妥协，用纵深防御补偿：
  - Turnstile 人机验证挂登录/注册/找回密码/发码 + 发帖/回帖（同时抑制自动化爆破）；未配置 `TURNSTILE_SECRET` 一律直通，发帖/回帖的校验发生在参数解析后、任何 D1 读写之前；
  - IP+账号双维度失败计数，5 次锁 15 分钟（D1 记录）；
  - `token_version` 改密全端吊销。
- **备选**：若 Cloudflare 后续开放原生 bcrypt/argon2 绑定且实测 CPU 占用可进 10ms 预算，切换实现（`PasswordHasher` 接口隔离，换算法不动业务代码）。
- **升级路径**：Workers 付费（$5/月）CPU 上限升至 30s，可无痛切换 Argon2id 并对存量懒升级重新哈希。
- **存量校验**：存量数据导入场景按旧格式 `md5(前端md5(明文) + salt)` 验证（前端预哈希行为迁移期保留，后续移除），验证通过后**透明重哈希**为 PBKDF2 新格式（懒迁移，无需用户改密）。
- **⚠ 重哈希 CPU 陷阱**：同一 invocation 内"验旧哈希 + 写新哈希"= 两次 PBKDF2 = 2× CPU，可能超墙；`waitUntil` 里的重哈希**仍占同一 invocation 的 CPU 预算**，不能靠它规避。对策：迁移窗口内验证旧格式后**不在登录请求内立即重算**，改为标记待升级、在**改密时**或独立的低频后台任务里升级到当前迭代数；只有注册/改密（本就单次哈希）走完整新格式写入。
- 哈希/验证只在登录、注册、改密三个低频接口发生，不影响列表页 CPU 预算。

## 9. 文件存储（R2）

### 9.1 桶与键规划

单桶 `freeidx-files`，按前缀分区：

```
avatar/{000uid补9位}/{uid}.png      ← 头像（uid 前 3 位分目录）
tmp/{uid}_{rand15}.{ext}            ← 上传暂存（status=0）
attach/{YYYYmm}/{rand}.{ext}        ← 正式附件（按年月分目录）
```

### 9.2 上传通道

上传走"前端 base64 → POST"（Workers 请求体上限 100MB，账户级限制，免费账户即 100MB），业务上限 ≤20MB（`upload_max_size` 进 kv 设置）；同时新增 multipart 支持。图片缩放/裁剪保持**客户端完成**（不依赖服务端图像处理，React 组件用 canvas 实现）。

### 9.3 暂存→关联流程

1. 上传 → R2 `tmp/` + `attach(status=0, uid)` → 返回 `{aid, url}`。
2. 编辑器插入图片 BBCode/Markdown 引用 `/attachments/{aid}/preview`（渲染端点，按 status 控制访问）。
3. 发帖/回帖带 `attachAids[]` → Worker 关联 pid/tid、`status=1`、R2 key 移到 `attach/YYYYmm/`、计数回写。
4. Cron 每日删除超 24h 的 `status=0`。

优点：无消息正文字符串替换（避免 aid 重用与并发问题），临时文件生命周期由表驱动而非会话驱动。

## 10. 前端架构（Pages + React 19 + Tailwind 4）

### 10.1 渲染策略（分阶段，收录为硬需求）

搜索引擎收录是明确需求（§16），而百度等引擎基本不执行 JS，**纯 SPA 不可作为 v1 交付形态**：

- **Phase 1（v1 交付）：SPA + 爬虫预渲染（写入期生成，非请求期 SSR）**。普通用户走 Vite 构建的 SPA（React Router 7 data router）；爬虫 UA（名单 + 行为特征）命中时返回**预生成的语义 HTML**。生成时机是**写入期**而非请求期：发帖/编辑时同步产出一份 SEO HTML（title/meta/canonical/JSON-LD/正文语义标签）存 R2（`seo/{tid}.html`），爬虫请求 = R2 get（I/O，不计 CPU）→ Cache API 前置。**刻意不在请求热路径跑 React `renderToString`**——整页 SSR 是纯 CPU，复杂帖页单次可能超 10ms 免费层墙；写入低频、把成本移到写时可使爬虫读路径 CPU 结构性归零。cache-miss（新帖尚未生成/冷内容）时用**模板字符串拼装**兜底（微秒级，非 React SSR）。
- **Phase 2（可选升级）：全量 Hybrid SSR**。所有请求走 React 19 流式 SSR（`renderToPipeableStream`）+ hydration，进一步提升 CWV 与首屏；因入口已在 Phase 1 打通，此升级为渐进式。
- `seo_title/seo_keywords` 字段随版块配置透传到预渲染 head。

### 10.2 路由设计

| 前端路由 | 页面 |
|---|---|
| `/` 与 `/page/:n` | 首页 |
| `/forum/:fid` | 版块页 |
| `/thread/:tid` `/thread/:tid/p/:page` | 主题详情 |
| `/thread/create/:fid`、`/post/:pid/edit` | 发帖 / 编辑 |
| `/login` `/register` `/resetpw` | 登录 / 注册 / 找回密码 |
| `/user/:uid`（含主题 tab）、`/me`（设置/改密/头像） | 用户主页 / 个人中心 |
| `/mod/:fid`（版务台）、`/admin/*` | 版务台 / 管理后台 |

URL 兼容：`.htm` 风格 301 重定向层（`thread-1-1.htm → /thread/1/p/1`）。因收录为硬需求，此层从"可选"升级为**建议必做**（存量站点迁移时继承旧 URL 权重，避免丢收录）。

### 10.3 组件与状态

- 布局：Bootstrap 4 栅格语义逐页翻译为 Tailwind 组件；响应式断点行为对齐（手机/平板/PC 自适应）；二级导航并入布局组件。
- 发帖器：TipTap 富文本，工具栏含图片上传（R2 通道）、代码插入（插入代码扩展 idx_insert_code）、引用回复（quotepid）；图片客户端裁剪/压缩组件、附件进度条。
- 已读标记：localStorage 记录已读 tid + 列表页角标，纯前端实现，无服务端成本。
- 登录/注册/找回密码/发码 + 发帖/回帖表单集成 Turnstile 组件：挂件在 `<Composer>` 内由 `turnstile` 开关按需挂载，发帖与回帖带 token、**编辑已有内容不带**（服务端编辑接口不校验）；官方 token 300s 过期且一次性消费，故每次提交（无论成败）都换发新 token；未配 `VITE_TURNSTILE_SITEKEY` 时挂件返回 null 且回调空串，与后端 `TURNSTILE_SECRET` 缺省直通对齐。
- 全局：`useAuth`（/api/me）、`forumList`（缓存 + access 过滤后）、i18n provider（zh-cn 默认，前台后台文案全覆盖）。

### 10.4 管理后台

React 路由 `/admin/*`，接口全部经 `admin_at` 校验；功能覆盖：站点设置、版块与权限矩阵、用户、用户组、主题管理、modlog、统计与缓存清理。

## 11. 后台任务与外部服务

### 11.1 Cron Triggers

| 频率 | 任务 |
|---|---|
| 每 5 分钟 | session GC（超 `online_hold_time` 清理）、在线数缓存刷新 |
| 每日凌晨 | today* 统计清零、临时附件 GC、queue GC、table_day 记录 |

### 11.2 队列（D1 queue 表）

预留异步任务通道（计数批刷、邮件投递重试），提供 `push/pop/gc` 三个原语；v1 消费端即 Cron 每 5 分钟批处理，不引入付费 Queues。

### 11.3 Email Provider（验证码/找回密码）：SMTP 账号池

Workers 无裸 socket，但 **`cloudflare:sockets`（TCP Sockets API）支持出站 TCP**：25 端口出站被封，**465（隐式 TLS）/587（STARTTLS）可用**——主流邮箱服务（QQ/163/企业邮/Gmail 等）SMTP 均为 465/587，**SMTP 方案可行**，采用账号池形态：

- **SMTP 账号池 + 轮询**（§19 决策 4 拍板）：后台配置多个 SMTP 账号（发件地址/服务器/端口/用户名/密码/**每日限额**），发信按 **round-robin 轮询**选择账号，把单账号免费额度扩为 N 倍（数量突破）；当前账号发送失败自动顺延下一账号（failover）。**每账号可设每日发送上限**（dailyLimit，0 为不限）：达到上限的账号当天轮询自动跳过（顺延其他账号，次日自动恢复），当日计数存 D1 kv `ext:email:cnt:{ymd}:{user}`（UTC 日切，成功发送才计数，读计数时顺带清理历史日期行）。选择策略采用轮询，分布更均匀。
- SMTP 客户端内置于 Worker（EHLO → STARTTLS? → AUTH LOGIN → MAIL FROM → RCPT TO → DATA），发送经 `waitUntil` 旁路**绝不请求内阻塞发信**；非 465/587 端口按明文连接（仅限本地联调用假 SMTP）。
- 池配置存 kv `ext:email:*`（config 明文 + 密码 AES-GCM 加密、永不回显），后台「站点设置 → 邮箱设置」零部署管理。
- 降级：池为空时等同关闭 `user_create_email_on`（注册不验证邮箱），流程完整可用。

## 12. 扩展（插件）机制

扩展能力重定义为"中间件/事件钩子 + 组件插槽 + 构建期选择性打包"：

| 概念 | 机制 |
|---|---|
| hook 注入点 | API：Hono 中间件注册表 + 生命周期事件（`post:created`、`thread:deleted`、`render:*`），扩展在 `apps/api/src/extensions/` 订阅；前端：组件插槽（帖子底部、侧栏等模板插槽位） |
| 源码级文件覆盖 | 不开放（破坏免费层可维护性）；模板级定制走主题 token + 组件替换配置 |
| 插件开关 | manifest.json + kv 表 `extensions` 配置 + 后台启停页 |

**v1 扩展点契约全集**（SEO/GEO 插件化核实后补齐，§16.4）：① 中间件注册 ② 生命周期事件 ③ `registerRoute`（Worker 路由：sitemap/llms.txt/验证文件/301 层）④ `registerCron`（定时任务：索引推送、掉单对账）⑤ `render:head(PageMeta)`（预渲染 head 片段贡献；核心定义 PageMeta 上下文 = 路由类型 + 实体数据 + setting 源）⑥ `robots:contribute`（robots.txt 片段贡献，核心装配引擎有序合并+去重）⑦ `bootstrap:contribute`（向 `/api/bootstrap` 聚合响应贡献字段，插件数据随核心一次下发、不产生额外请求——广告位配置即用此点，§17）⑧ 前端组件插槽。官方应用：支付四插件（§15.5）、seo/geo 插件（§16.4）、ads 插件（§17）。

支付通道是该扩展机制的首批官方应用：**PayPal/Stripe/支付宝/卡密各自是独立插件**（独立 manifest + 配置命名空间 + 生命周期），payment-core 只提供契约/注册表/订单状态机（§15.5 L1 配置级热插拔）；付费档可经 Dynamic Workers 沙箱让第三方通道插件以同一粒度代码级热加载（§15.5 L2）。

v1 内置能力分两类处理：**富文本编辑器、人机验证、精华、我的回帖、已读标记、二级导航、插入代码七项功能并入 v1 核心**（逐项映射见附录 B）；搜索、标签、第三方登录等长尾能力不作为 v1 目标，但保留同等扩展点使其**可被重写**。


Pages 项目绑定 `apps/web`，构建命令 `pnpm --filter web build`，预览部署 + 生产分支保护。

### 13.2 域名与路由（同域方案）

自定义域 `bbs.example.com`：
- `/`、`/assets/*` → Pages
- `/api/*`、`/files/*` → Worker（Zone Routes / 子域名均可；若用 `api.` 子域需配 CORS + SameSite=None 权衡，推荐同域反代）

### 13.3 安装与迁移

Workers 无文件系统，传统 Web 安装向导不可行，部署即安装：

1. `wrangler d1 create freeidx` → `wrangler d1 migrations apply`（建表）。
2. `pnpm seed`：写入预置用户组/默认版块/forum_access 矩阵，并以 CLI 交互创建**首个管理员**（gid=1，PBKDF2 新哈希直接入库，无懒升级链路）。
3. `wrangler secret put`（JWT 密钥、Turnstile secret；邮件 SMTP 池凭据走后台加密 kv，无需 secret put）。
4. 存量数据导入：`tool/migrate.ts` 读取旧站 MySQL dump（含存量数据导出）→ 生成 D1 INSERT；密码不迁移明文（md5 兼容链路已保证存量用户可直接登录并懒升级哈希）；存量 `message_fmt` 直接沿用（渲染结果天然兼容 UBB/HTML 老帖）；附件文件按旧目录结构批量 `r2 object put` 并回填 attach 表 key。

### 13.4 CI/CD

GitHub Actions：PR → 类型检查 + 单测（权限引擎与 message_fmt 重点覆盖）→ D1 migration dry-run；main → 构建 Pages 预览 + Worker 预览；手动门禁 → `wrangler deploy --env prod`。

### 13.5 可观测

免费层方案：Worker `tail`（wrangler tail 排障）+ runtime 统计页 + D1 查询耗时打点。

### 14.2 阶段风险与对策

1. **D1 写入额度（10 万行/天）与单库 500MB**：浏览量/计数批刷（§7）；上线后用 runtime 页监控写行量；内容规模逼近 30 万行时启动 §18.2 P1 升级。
2. **单请求 50 条 D1 查询上限（免费）**：`DB.batch()` 聚合 + 查询计数器单测防回归（§7）。
3. **Workers 10 万请求/天**：列表接口返回聚合数据（一次请求拿 thread+posts+附件+广告位配置），图片直链走 Cache API。
4. **CPU 10ms 硬上限**：三类纯计算路径需护栏——① 密码哈希迭代数受此约束（§8.4，含重哈希 2× CPU 陷阱对策）；② 爬虫渲染**移到写入期预生成存 R2 + Cache API**，请求期不跑 React SSR，cache-miss 用模板串兜底（§16.1）；③ sanitize/解析写时定稿存 `message_fmt`，读路径零重算（§8.3）。I/O 等待不计 CPU，故稳态读请求 <2ms；CI 加子请求+CPU+rows_read 三预算断言防回归（§7）。
5. **支付 webhook 可靠性**：验签+幂等（provider_ref 唯一约束）+ 掉单对账 cron（§15）。

### 14.3 执行顺序总原则（八条依赖前置铁律）

一句话顺序：**表结构 → 权限引擎 → 预算守卫 → 共享契约 → 只读接口 → 前端只读页 → 扩展点契约 + seo 一期 → 鉴权 → 写时定稿 → 写接口 → 附件 → SEO 生成侧 → 版务/后台 → cron/queue → 长尾 + 迁移 + 压测 → geo/seo 二期 → 会员与支付通道 → M6 可选**。

| # | 规则 | 依据 | 违反的代价（为何不能后补） |
|---|------|------|------------------------------|
| 1 | **表结构一次定稿**：`0001_init.sql` 建全部表（核心 17 张 + vip_plan/order/point_log/card/ad_slot + email_code），含 `thread.digest`、反规范化 `username/lastusername/avatar`、`attach.status`、覆盖索引 `(fid,lastpid)`/`(fid,tid)`，同批建 seed | §5.2、§5.4、§18.3 | 上线后加列需增量迁移 + 历史行回填 + 双写窗口；M4 存量导入要重跑一遍 |

## 15. 会员体系（v1 新增）

会员体系建立在 user/attach 表预留的 `credits/golds/rmbs` 积分字段与 101-105 等级组骨架之上（user/attach 表已有积分字段但无获取/消费逻辑），补全获取/消费/支付闭环，**不改动组权限模型**。

### 15.1 功能范围

| 模块 | 设计 |
|---|---|
| 等级体系 | gid 101-105 按发帖量自动升级（§6.3）；等级徽章随 post 渲染 |
| 积分 credits | 获取：发主题/回帖/每日首帖（数值后台可配，kv `setting`）；消费：付费附件下载。所有变动写 `point_log` 流水（含幂等键，防重复发放），禁止裸改 user.credits |
| 付费附件 | 上传者设置 credits 价格（0=免费）→ 下载时扣积分；上传者本人/版主/VIP 免扣（可配）；downloads 计数与 allowdown 权限按核心权限模型 |
| VIP 会员 | `vip_plan` 计划表（月/季/年：name/duration_days/price_cents/perks JSON）；权益：VIP 徽章、附件免积分、上传限额倍率、签名档；VIP 用户挂专用组（gid=106，**复用 group 权限矩阵**表达权限差异，不另建权限体系）；`user.vip_expire_at` 到期由 cron 回落原组 |
| 订单与支付 | `order` 表（order_no/uid/plan_id/amount_cents/currency/status/provider/provider_ref/created_at/paid_at）；**每个支付通道是一个独立插件**：card（卡密，v1 必做零依赖）与 paypal / stripe / alipay 各自独立 manifest/配置/启停，核心只含契约与注册表，详见 §15.5。支付成功 → 延长 vip_expire_at / 充值积分 |
| 后台 | 计划 CRUD、订单查询与手动补单、卡密批量生成、积分手动调整（强制填理由、留流水）、VIP 用户列表 |

### 15.2 新增表

`vip_plan`、`order`、`point_log`、`card`（均 D1；金额一律 INTEGER 最小货币单位；order.provider_ref 唯一索引做 webhook 幂等；point_log 建 (uid, id) 索引支撑"我的积分明细"分页）。

### 15.3 关键约束

- 支付回调是公网 webhook：`POST /api/payments/webhook/{provider}`，先验签后处理，处理必须幂等（重复回调直接返回成功）。
- 积分增减在 `DB.batch()` 事务内完成（余额更新+流水同批），发放入口挂在 §12 生命周期事件（`post:created`）上，与自动升组同一钩子链。
- 掉单对账：cron 每小时拉取 provider 侧近 24h 成功支付比对本地 `status=pending` 订单（卡密除外）。
- 合规提示：Stripe/PayPal 需海外账户（不服务中国大陆商户主体）；支付宝当面/网页支付需国内企业或个体工商户资质 + ICP 备案站点——通道启用与站点主体/受众联动（§19 决策）；未启用通道在收银台自动隐藏。

### 15.4 API

`GET /api/vip/plans`、`GET /api/payment-providers`（收银台可用通道列表 = payment-core 聚合已启用插件，随 bootstrap 下发）、`POST /api/orders`（下单，body 含 provider 插件 id，返回跳转/二维码/卡密输入态）、`POST /api/orders/{no}/redeem`（卡密兑换）、`GET /api/orders/{no}`（前端轮询兜底 webhook 延迟）、`GET /api/me/points`（余额+流水）、`POST /api/payments/webhook/{pluginId}`；admin：`/api/admin/vip/*`、`/api/admin/orders`、`/api/admin/cards`、`/api/admin/extensions/{id}`（通用插件启停/装卸/配置，支付插件走此通道）。

### 15.5 支付插件化与热插拔（每个通道 = 一个独立插件）

**形态原则**：核心不含任何通道代码。PayPal、Stripe、支付宝以及卡密兜底**各自是一个独立插件**——独立 manifest、独立配置命名空间、独立生命周期（安装/启用/停用/卸载），互不打包、互不依赖（§12 扩展机制的首批官方应用），未来第三方通道（微信支付等）以同样粒度接入。

#### 插件目录结构

```
apps/api/src/extensions/
├── payment-core/        # 非插件：PaymentProvider 契约 + 注册表 + 订单状态机
│                        #   + webhook 分发 + 对账/退款编排（通道无关）
├── card/                # 卡密插件（官方，出厂 enable=1，零外部依赖兜底）
├── paypal/              # 各插件结构相同、彼此独立：
├── stripe/              #   manifest.json   # 能力与配置声明
└── alipay/              #   index.ts        # PaymentProvider 实现
                         #   config-schema.ts# Zod schema → 后台动态渲染配置表单
```

manifest.json 示例：

```json

  "name": { "zh-cn": "支付宝", "en-us": "Alipay" },
  "version": "1.0.0",
  "installed": 1,
  "enable": 0,
  "dependencies": { "payment-core": ">=1.0" },
  "capabilities": { "currencies": ["CNY"], "modes": ["qrcode", "redirect"], "refund": true }
```

#### 插件独立性保证

| 维度 | 设计 |
|---|---|
| 生命周期 | 每插件独立 install/enable/disable/unstall；后台扩展页逐一列出，停用一个不影响其他 |
| 配置隔离 | kv 命名空间 `ext:{pluginId}:config`（非敏感）+ `ext:{pluginId}:secret`（AES-GCM 加密）；插件只读写自己的命名空间；配置项由各自 configSchema 声明，后台动态渲染表单，**核心不硬编码任何通道参数** |
| webhook 分发 | `/api/payments/webhook/:pluginId` → 注册表按 id 查找（要求 installed+enable），未安装 404、已停用 410；不存在统一的"支付插件"总入口 |
| 收银台聚合 | 核心运行时聚合已启用插件（按 capabilities.currencies / 地区 / UA 过滤 + 排序展示），通道名称/图标来自各 manifest |
| 构建 | 四个官方插件独立模块，构建时经 `PAYMENT_PLUGINS` 清单选择性打包（不启用站点可裁剪包体）；插件间零 import |

#### 两级热插拔

```
L1 配置级（v1，免费层可用）
   官方插件代码构建时打入 Worker 包；install/enable/disable/unstall 只改 kv 状态，
   零部署、秒级生效；unstall = disable + 清除本插件 kv 命名空间
   （订单/流水属核心数据，保留）。

L2 代码级（P1 付费档可选，M6+ 探索）
   每插件即一个独立可加载模块包（粒度天然吻合单插件）：上传 R2 + 签名校验 +
   Dynamic Workers（open beta，仅付费）沙箱执行；第三方通道插件只走 L2 形态。
   安全边界：动态插件不持有 DB/Secret 绑定，只做协议适配（组包/签名/验签/
   解析回调），资金落账与订单状态机永远由 payment-core 执行。
```

#### PaymentProvider 契约（payment-core 提供，类型在 packages/shared）

```ts
interface PaymentProvider {
  id: string;                       // 与 manifest.id 一致
  createCheckout(order, cfg): Promise<
    | { mode: 'redirect'; url: string }     // Stripe Checkout / PayPal approve
    | { mode: 'qrcode'; content: string }>; // 支付宝扫码
  verifyWebhook(req, cfg): Promise<ProviderEvent | null>; // 验签失败返回 null
  queryOrder?(ref, cfg): Promise<ProviderOrderStatus>;    // 对账用
  refund?(order, cfg): Promise<RefundResult>;
}
// cfg = 该插件 configSchema 解析结果（含解密后密钥），由核心注入，插件不自取全局配置
```

#### 各插件实现要点

| 插件 | 集成方式 | 签名/验签 | 交互 | 资质门槛 | Workers 注意点 |
|---|---|---|---|---|---|
| card | 核心 card 表 + 兑换码 | 无 | 输入表单 | 无 | 出厂 enable=1，保证站点任何情况下可收款 |
| paypal | Orders API v2 纯 REST fetch（无重 SDK） | webhook 证书 RSA 验签（cert_url 拉证书，WebCrypto RSASSA-PKCS1-v1_2 SHA-256） | redirect | PayPal 商家账户，跨境友好 | 证书缓存写本插件 kv 命名空间（TTL 24h） |
| stripe | 官方 `stripe` npm（支持 Workers）或直连 REST；Checkout 托管收银台 | webhook HMAC-SHA256（WebCrypto 原生，最简） | redirect | 海外主体/个人可申请 | SDK 包体超限时降级直连 REST |
| alipay | openapi.alipay.com 网关直连 REST + 自封装 RSA2 签名（官方 Node SDK 依赖重，不引入） | 请求 RSA2 签名 + 异步通知验签（RSASSA-PKCS1-SHA256，公钥模式，弃证书模式） | PC 扫码 / WAP redirect | 国内企业/个体工商户 + ICP 备案 | 中文参数按网关规则 encode；沙箱（openapi-sandbox.dl.alipaydev.com）联调 |

订单状态机（pending→paid→fulfilled/refunded）、webhook 幂等（provider_ref 唯一约束）、前端轮询兜底、cron 掉单对账、后台退款编排全部沉在 payment-core；**每个插件的通道差异收敛在 createCheckout/verifyWebhook 两个函数内**——这是插件能独立装卸的结构基础。

#### 密钥管理（每插件独立、热换不部署）

- 敏感密钥（secret key、RSA 私钥）：AES-GCM 用 master key 加密后存 `ext:{pluginId}:secret`；master key 存 wrangler Secret。各插件密钥互相隔离，停用/卸载不波及其他通道。
- 后台"更换密钥" = 重新加密写该插件命名空间，即时生效；私钥永不出现在响应/日志；L2 动态插件拿到的是核心代签结果而非私钥本身。

#### 演进判断

v1 交付 L1：四个独立插件（card 出厂启用；paypal/stripe/alipay 出厂安装但停用，后台填密钥即热启用）。插件粒度与 L2 一致，未来升级代码级热插拔**无需重新拆分**。L2 仅在出现第三方通道真实需求且已升级付费档时启动（open beta 风险 + 资金安全审查成本高，不为假想需求预建）。

## 16. SEO 与 GEO（搜索引擎 + AI 引擎收录，硬需求）

### 16.1 渲染前提（修正 v1 形态）

百度基本不执行 JS、Google 渲染队列有延迟，**纯 SPA 不满足收录要求**。v1 采用**爬虫预渲染**（§10.1）：识别爬虫 UA（名单 + 特征）→ 返回**写入期预生成**的语义 HTML，而非请求期跑 React SSR。约束与对策：
- 免费层 CPU 10ms 装不下大帖的 `renderToString` → **生成时机移到写入期**：发帖/编辑时产出 SEO HTML 存 R2（`seo/{tid}.html`），爬虫读路径 = **Cache API 前置（TTL 1h）→ R2 get（I/O 不计 CPU）**，**请求期 CPU 结构性归零**。边缘层按 §7 核实结论只有 `max-age` 有效（Workers 内没有网络级按 URL 主动失效，写路径只删 R2 产物 `deleteThreadSeoHtml`），故**编辑后爬虫侧最多 1h 才看到新 HTML**——收录场景可接受，人类请求不经此层。
- cache-miss（新帖/冷内容未生成）用**模板字符串拼装**兜底（微秒级），绝不在热路径触发 React SSR；渲染包 try/catch，失败回落 SPA 壳 + 最小模板，不让爬虫拿到 1102。
- 普通用户仍走 SPA（交互体验与 Worker 额度最优）；M6 可升级全量 SSR。
- 预渲染只对白名单爬虫 UA 生效，防止被伪造 UA 刷渲染消耗额度（配 Turnstile bot score 辅助判定）。

### 16.2 SEO 技术清单（对应各大搜索引擎收录要求）

| 项 | 实现 |
|---|---|
| sitemap | Worker 动态生成 `/sitemap.xml`（sitemap index 分片，每片 ≤5 万 URL，带 lastmod，按 thread.last_date 输出） |
| 主动推送 | cron 每日推送新增/更新 URL：Bing **IndexNow**（key 文件放 public/）、百度普通推送 API（token 存 Secret）；Google 依赖 sitemap+抓取 |
| meta 体系 | 每页唯一 title/description；版块页读取 `forum.seo_title/seo_keywords` 配置；canonical 全页面输出；OG + Twitter Card（帖子标题/作者/首图） |
| 结构化数据 | JSON-LD：`WebSite`(+SearchAction)、`BreadcrumbList`（首页>版块>主题）、`DiscussionForumPosting`（首帖：author/dateCreated/headline）、`Comment`（回帖列表）——同时是 Google 富摘要与 AI 引擎引用的关键信号 |
| URL 规范 | 语义化稳定 URL；`.htm` 旧链 301（继承原站权重）；分页 `?page=` + canonical 指向规范页；参数页（keyword 高亮等）noindex |
| 性能 CWV | 静态资源 `immutable` 长缓存、图片 WebP+lazy+显式宽高（防 CLS）、字体子集化、广告位占位固定高度（§17） |
| 站点验证 | 后台可配 Google/Baidu/Bing 验证 meta 与验证文件内容（存 kv，预渲染注入 + `/.well-known` 路由输出） |
| robots.txt | Worker 动态输出（AI 爬虫开关变更即时生效，无需重新部署） |

### 16.3 GEO（生成式引擎优化：Google AI Overviews、ChatGPT、Perplexity、百度 AI 搜索等）

| 项 | 实现 |
|---|---|
| llms.txt | Worker 动态生成 `/llms.txt`：站点简介、版块目录、精华帖入口、内容许可声明 |
| AI 爬虫策略 | 核心策略名单（唯一事实源 `core/crawler.ts` 的 `POLICY_CRAWLERS`，共 15 条，按「抓取结果服务于谁」分档）：**训练/索引型默认不给正文**（GPTBot、ClaudeBot、Claude-Web、PerplexityBot、CCBot、AI2Bot）、**检索/用户服务型默认给正文**（Bytespider、Amazonbot、Amzn-SearchBot、Amzn-User）、**AI 助手检索/用户触发型默认给正文**（ChatGPT-User、Claude-User、Perplexity-User、OAI-SearchBot）、**robots 专用 token**（Google-Extended，不作为 UA 出现，只写声明）。后台开关默认允许；关掉后**声明与执行双管齐下**：robots.txt 写 `Disallow: /`，同时页面请求直接 403（预渲染产物不再供给），开关名副其实 |
| 无 JS 可提取 | 预渲染 HTML 正文用语义标签（article/header/nav/time/footer），不套登录墙；精华帖可配置"全文对爬虫开放"提升被引用率 |
| 引用友好 | 每帖固定 permalink + 楼层锚点（`#pid`）；作者、发布时间、编辑时间机器可读（JSON-LD + `<time datetime>`） |
| 事实密度 | 列表页输出结构化摘要（标题+版块+作者+日期+回帖数），便于 AI 引擎抽取；避免纯图片/纯附件承载关键内容 |
| 一致性 | 站名、logo、简介在 head/JSON-LD/llms.txt/OG 四处一致（同一 kv setting 源） |

### 16.4 SEO / GEO 插件化拆分（可行性核实结论）

**结论：可行。拆成 `seo`、`geo` 两个独立官方插件**（与支付插件同一套 manifest / kv 命名空间 / 生命周期模型，§15.5 同构），但必须满足三个前提：

1. **收录保底留在核心、不可停用**——SEO 是硬需求（§16 开头），插件误停不能导致站点丧失基本收录能力；
2. **核心补齐四类扩展点**——现有 §12 机制（中间件+生命周期事件+组件插槽）不足以承载 SEO/GEO，需新增 `registerRoute` / `registerCron` / `render:head(PageMeta)` / `robots:contribute`（已并入 §12 契约）；
3. **共享产物唯一归属，冲突由核心仲裁**——robots.txt 是单文件而两插件都要写：核心提供**装配引擎**（片段贡献+有序合并+去重）；JSON-LD 归 seo 插件，geo 只消费不重复输出；爬虫 UA 识别由核心统一分类（searchbot / aibot / human），插件不自维护名单。

#### 逐项归属核实表

| §16 功能项 | 归属 | 可插件化 | 理由 / 依赖扩展点 |
|---|---|---|---|
| 爬虫预渲染管线（§16.1） | 核心 | ✗ | 渲染基础设施本身，停用即放弃收录 |
| 语义 HTML / 无登录墙 / 无 JS 可提取 | 核心 | ✗ | React 组件树结构，非运行时注入 |
| 每页唯一 title/description、canonical、分页 noindex | 核心 | ✗ | 收录基本盘，数据源即页面实体 |
| permalink + 楼层锚点 + 机器可读时间 | 核心 | ✗ | 帖子组件结构的一部分 |
| robots.txt 输出 | 核心（装配引擎） | ⚠ 片段可贡献 | seo 贡献 `Sitemap:` 行、geo 贡献 AI 爬虫规则，核心合并去重 |
| 爬虫 UA 分类 | 核心 | ✗ | 预渲染管线与两插件共用同一分类结果 |
| 性能 CWV（长缓存/WebP/字体/CLS） | 核心（构建层） | ✗ | Vite/Tailwind 工程配置，无运行时形态 |
| sitemap.xml（分片+lastmod） | **seo 插件** | ✓ | registerRoute + D1 读 |
| JSON-LD（WebSite/Breadcrumb/DiscussionForumPosting/Comment） | **seo 插件** | ✓ | render:head(PageMeta)；geo 引用同一份，不重复输出 |
| OG / Twitter Card | **seo 插件** | ✓ | render:head(PageMeta) |
| `.htm` 旧链 301 层 | **seo 插件** | ✓ | registerRoute（中间件形态） |
| IndexNow / 百度主动推送 cron | **seo 插件** | ✓ | registerCron + Secret token |
| 站点验证 meta / 验证文件 | **seo 插件** | ✓ | render:head + registerRoute（`/.well-known`、根验证文件） |
| llms.txt | **geo 插件** | ✓ | registerRoute |
| AI 爬虫开关（名单见 §16.3，共 10 个） | **geo 插件** | ✓ | robots:contribute（声明）+ useMiddleware 拒绝闸门（执行：关掉即 403）；名单归属核心，插件不自维护 |
| 精华帖"全文对爬虫开放"策略 | **geo 插件** | ✓ | 预渲染过滤钩子（消费 PageMeta） |
| 列表页事实密度（结构化摘要） | 核心（API+组件契约） | ⚠ | 数据形状由核心 API 固定，插件不改列表 DOM |
| 站名/logo/简介四处一致 | 核心 kv setting 单一源 | ✓ 双方消费 | seo（head/JSON-LD/OG）与 geo（llms.txt）读同一 setting |

#### 插件行为语义

- 两插件**出厂启用**（官方插件，同 card 支付插件形态），后台可独立停用，互不影响：
  - 停用 seo：sitemap/JSON-LD/OG/301/推送消失，核心保底（title/canonical/预渲染/语义 HTML）仍在 → 基本收录保留，失去富摘要与旧链权重继承；
  - 停用 geo：llms.txt 404、AI 爬虫 robots 片段回落核心默认策略（默认允许/拒绝见 §19 决策）。
- 依赖方向：两插件各自依赖核心契约（PageMeta、robots 装配引擎），**互相零依赖**（同支付插件独立性原则）；唯一交集 `Sitemap:` 行由 seo 贡献给装配引擎，geo 不感知。
- L2 展望：两插件均为纯服务端逻辑、无资金安全问题，第三方可按 Dynamic Workers 形态重写/扩展（如其他搜索引擎推送、自定义摘要协议）。

#### 对路线图的影响

扩展点契约（PageMeta / registerRoute / registerCron / robots 装配引擎）必须在 **M1** 与预渲染管线同期定型，否则 seo 插件无法落地；seo 插件一期（sitemap/JSON-LD/OG/301）随 M1 收录基座交付，二期（推送 cron/验证配置）与 geo 插件在 M4（§14 已更新）。

## 17. 广告系统（自定义广告位 + Google AdSense，独立插件）

广告系统整体是一个独立官方插件 `ads`，与支付/seo/geo 插件同构（同一套 manifest / kv 命名空间 / 生命周期 / 后台扩展页）。**出厂 installed=1、enable=0**（论坛默认无广告；需变现且已具备资质时由管理员启用），后台可独立启停、卸载，不影响核心与其他插件。

### 17.1 插件形态与独立性

```
apps/api/src/extensions/ads/
├── manifest.json     # id="ads"，capabilities={positions:[…],types:["html","image","adsense"]}
├── index.ts          # 订阅 bootstrap:contribute（服务端）+ 注册前端组件插槽渲染器
└── config-schema.ts  # Zod：AdSense client id / ads.txt 发布商 id / CMP 开关 / 各位置默认占位高
```

| 维度 | 设计 |
|---|---|
| 生命周期 | 独立 install/enable/disable/unstall；后台扩展页与其他插件并列。停用 = `bootstrap:contribute` 不再注入 ads 字段，前端插槽渲染为空（占位收起），核心与页面无残留 |
| 配置隔离 | kv 命名空间 `ext:ads:config`（非敏感：位置开关/占位高/CMP）+ `ext:ads:secret`（AdSense client id、ads.txt 发布商 id 等，AES-GCM）；核心不硬编码任何广告参数 |
| 服务端注入 | 经 §12 扩展点 **`bootstrap:contribute`** 把已启用广告位配置挂到 `/api/bootstrap` 聚合响应，**不产生额外请求**（Workers 10 万请求/天额度敏感） |
| 前端渲染 | 经 §12 **组件插槽**（header/footer/sidebar/thread_top/thread_bottom/post_between/forum_list_between）按位置渲染；插件提供 `<AdSlot position>` 组件，插槽无数据即不占位 |
| 数据表 | `ad_slot` 表在核心 0001_init 建表（与 order/card 同策略：schema 归核心、数据归插件），插件独占读写；unstall 保留表结构与历史数据、仅清 `ext:ads:*` kv（重装可恢复投放） |
| 构建 | 独立模块，`OFFICIAL_PLUGINS` 清单选择性打包；与其他插件零 import |

### 17.2 数据模型

`ad_slot` 表：id、position、type、config(JSON)、enabled、sort、start_at/end_at（定时上下线）。

位置枚举（前端组件插槽渲染）：
`header`、`footer`、`sidebar`、`thread_top`（帖子列表上方）、`thread_bottom`、`post_between:{n}`（帖内每 n 楼插入）、`forum_list_between`（列表每 n 行插入）。

### 17.3 广告类型

| type | config | 渲染与安全 |
|---|---|---|
| `html` | 自定义 HTML 片段 | 仅 gid=1 后台可录入；**不走用户内容 sanitize 通道**（管理员信任链，与 doctype=0 放行一致），录入页明示风险 |
| `image` | 图片 URL（R2 上传或外链）/落地页/alt | `<a><img>` 组件，移动端自适应 |
| `adsense` | data-ad-slot、format、responsive | 全局 `adsbygoogle.js` 只加载一次（异步），每广告位 `<ins class="adsbygoogle">` push；未配置 client id 时自动隐藏全部 adsense 位 |

### 17.4 投放与性能

- `ads.txt` 由插件经 `registerRoute` 输出（或落 Pages `public/`），发布商 ID 存 `ext:ads:secret`；后台设置页可填。
- CLS 防护：每个广告位预留固定 min-height 占位（占位高来自 configSchema）。
- GDPR/CCPA 地区投放 AdSense 需 CMP 同意横幅——插件内置可选简单同意组件（存 localStorage + `data-ad-requested-with-consent`），完整 TCF v2.2 CMP 列为 M6 可选（§19 决策）。
- runlevel 关站时 `bootstrap:contribute` 短路、广告自动停投；爬虫预渲染**不注入** AdSense 脚本（避免违反 AdSense 政策与干扰收录）。
- 停用插件即全站零广告且无占位残留——这是"广告位系统作为独立插件"的核心收益。

### 17.5 API 与后台

`GET /api/bootstrap`（启用时含 `ads` 字段，由插件贡献）；admin：`GET/POST/PUT/DELETE /api/admin/ad-slots`（插件经 `registerRoute` 注册，鉴权 gid=1）、预览模式（`?ad_preview=1` 仅管理员可见草稿位）；插件启停/配置走通用 `/api/admin/extensions/ads`。

## 18. 容量评估：百万级内容能否支撑

### 18.1 容量模型（假设 100 万内容行 = 10 万主题 + 90 万回帖，平均每帖 message+message_fmt ≈ 3KB）

| 资源 | 百万内容的需求 | 免费层供给 | 结论 |
|---|---|---|---|
| D1 存储 | 数据 3-4GB + 索引 ≈ **4-6GB** | 单库 500MB | **不满足**，是第一个撞到的墙 |
| D1 行读取 | 详情页 miss 时 ≈40-60 行；列表页反规范化后单表 ~30 行、匿名流量走 Cache API 边缘缓存**零 rows_read** | 500 万行/天 | 缓存命中后实际读远低于裸算，≈8-12 万次详情 miss/天为上限（§7/§18.3） |
| Workers 请求 | SPA 每 PV ≈4-8 次 API 调用（bootstrap 聚合后）；**边缘缓存命中同样计一次请求**（省的是 CPU 与 D1/KV/R2 子请求，不是请求额度，§7） | 10 万/天 | ≈1.5-2.5 万 PV/天；边缘层须绑自定义域才生效（§7） |
| R2 附件 | 图片为主：10GB ≈ 2-5 万张 | 10GB + 零出站费 | 基本满足，可按需清理 |
| CPU | 稳态读请求 <2ms（纯 I/O + JWT/序列化）；三类计算路径已移出热路径或护栏化 | 10ms/请求 | 满足（§8.3 写时定稿 / §8.4 哈希留余量 / §16.1 写入期预渲染） |

**结论：免费层支撑约 ≤30 万内容行、≤1 万 PV/天 的论坛正常运行；"百万内容 + 常态访问"必须进入付费档（成本仍很低），但架构无需推翻——所有优化点在设计中已预留。**

### 18.2 三档扩展路径（平滑升级，不改架构）

| 档 | 适用规模 | 方案 | 月成本 |
|---|---|---|---|
| **P0 免费层** | ≤30 万行、≤1 万 PV/天 | 本设计默认形态：三层缓存全开、计数批刷、聚合接口 | $0 |
| **P1 Workers Paid** | 100 万-500 万行、≤10 万 PV/天 | $5 计划：CPU 上限 30s（密码哈希可升 Argon2id）、请求按量 $0.30/百万、**D1 含 10GB 存储/库 + 50 亿行读/月 + 读副本**（读写分离，副本承接全部读流量）；R2 超量按 $0.015/GB | $5-15 |
| **P2 冷热分层** | >500 万行或逼近单库 10GB | 热数据（近 90 天 + 精华 + 置顶 + 全部索引/计数）留 D1；冷帖正文归档 R2 JSON（`archive/thread/{tid}.json`），详情页 miss D1 后走 R2 + Cache API（TTL 7 天）——`table_day` 冷热分表即此思路雏形；列表/搜索永远只查 D1 索引列 | +$1-5 |
| P3 兜底 | 极端规模 | D1 按版块分库（付费可建大量库）或外置 serverless Postgres；破坏全-CF 简单性，非必要不采用 | — |

### 18.3 v1 即落地的优化（不分档位，全部内置）

1. **游客只读接口 + 爬虫预渲染 HTML 走 Cache API 边缘缓存**（列表 30s、详情 60s、爬虫页 1h），命中即对 D1 零 rows_read——首要读取削减手段（§7 读取屏障，已落地 `core/cache/edge.ts`）。
2. 聚合接口 + `DB.batch()`（50 查询/请求预算，§7）；bootstrap 一次下发广告位/版块/用户。
3. **thread 反规范化 username/lastusername/avatar**（§5.2）→ 列表页单表扫描、零 JOIN、零 user 二次查，rows_read 砍半。
4. 详情页边缘缓存 `max-age=60` 而非 SWR（§7 核实：`stale-while-revalidate` 对 `cache.match`/`cache.put` 不支持，Workers 内也无网络级按 URL 主动失效）；写后的即时刷新由前端 TanStack Query 失效承担，登录用户请求本身绕开边缘缓存。
5. 浏览量/回帖计数 isolate 内攒批，5s 或请求结束合并写库（§7 runtime 行）。
6. **深分页用游标不用 OFFSET**：OFFSET 跳过行仍计 rows_read（实测 `OFFSET 50000` 读 50,020 行 vs 游标 ~23 行）；">100 页倒排" + 游标式 `?before_tid=`，杜绝 `OFFSET 100000` 类全扫。
7. 列表页覆盖索引：`(fid,lastpid)`、`(fid,tid)` 只取列表列（索引可减少 rows_read）；禁 `SELECT *`，message/message_fmt 大字段仅详情页按 pid 读取。
8. 搜索预留 FTS5 虚拟表（D1 支持），百万行下替代 `LIKE '%x%'` 全表扫描——M6 启用。
9. 附件本体永不进 D1（R2 + Worker 代理 + Cache API，§9）。

### 20.2 深挖发现：lastusername 结构性 bug（🔴 级，影响全站主题）

`lastusername` 全项目唯一写入点 = 发帖 INSERT（值=楼主名）；而回帖更新尾列、待审回帖过审补列、删末尾回帖回退（两分支）三条维护 `lastpid/lastuid/last_date` 的语句**全部漏 `lastusername`** → 列表页"最后回复 by X"自主题创建起恒显示楼主名（纯显示层错误，`lastuid` 跳转正确掩盖了它）。与改名场景无关、影响全站存量主题。用户快照三层全景：

| 层 | 载体 | 陈旧边界 | 处置 |
|---|---|---|---|
| L1 D1 列 | `bbs_thread.username/avatar/lastusername`（全库唯一含用户快照列的表） | admin 改名 | avatar 已有 backfill；username/lastusername 由批次 2 补齐 |
| L2 R2 | `seo/{tid}.html` 烧录作者名（generate.ts） | 改名不触发重建 | 接受 ≤1h 陈旧（与边缘缓存 TTL 同量级）；批量重建留 C 档暂缓 |
| L3 HTML | 回帖 `message_fmt` 引用块烧录被引用者名+头像 URL | 改名后永久旧名 | 接受（写时定稿语义，与 §8.3 CPU 归零原则一致） |

改名全仓唯一路径 = `PUT /api/admin/users/:uid` username 分支；用户无自助改名端点（改名极低频，读多写少取舍成立，见 §5.2）。
