# 部署与发布

本文说明生产发布流水线 [.github/workflows/deploy.yml](../.github/workflows/deploy.yml) 的配置、触发方式、总开关与常见问题。

## 1. 流水线概览

```
push main / 手动触发
        │
        ▼
   [ci] 门禁（复用 ci.yml：typecheck / i18n / test / 迁移 dry-run / lint）
        │
        ▼
   [deploy] 前置检查 → 开通或复用 D1/KV → 回填 wrangler.toml
            → 应用迁移（每次运行）→ 导入 seed（可选）→ 迁移门禁（远程库有未应用迁移则中止）
            → 构建前端 → wrangler deploy → 配置 R2 生命周期 → 写入运行摘要
```

设计要点：

- **门禁是单一事实源**：`deploy` 通过 `needs: ci` 复用 [ci.yml](../.github/workflows/ci.yml)，CI 红灯时生产不会发布。
- **D1 / KV 的 ID 不进仓库**：流水线每次运行时用 `wrangler d1 list` / `wrangler kv namespace list` 解析出真实 ID，再用 `sed` 回填到构建工作区；仓库里 [wrangler.toml](../apps/api/wrangler.toml) 保持占位值 `00000000-0000-0000-0000-000000000000`。
- **前后端一次部署**：前端 `apps/web/dist` 作为 Worker 的静态资源（`[assets]`）一起上线，只有一个 Worker。
- **迁移必须先于 Worker**：Worker 的 `SELECT` 直接引用迁移新增的列（如 `0024` 的 `bbs_forum.lang`），顺序反了会让 `GET /api/bootstrap` 与版块列表直接 500。因此每次运行都会先执行 `wrangler d1 migrations apply freeidx --remote`；它只在 `d1_migrations` 表中未登记的文件上执行，已应用的文件自动跳过，不会重复或删除既有数据（唯一一处 `DROP` 是回收从未被读写的空表 `bbs_login_fail`）。`wrangler deploy` 前还有「迁移门禁」硬检查，远程库存在未应用迁移会直接中止。`forumlist` 走 L0 + L2 缓存（TTL 300s），发版后最长 5 分钟内前台仍按「未绑定」处理新字段——后台保存任意版块会立即失效该缓存。
- **运行时密钥不在流水线里**：`JWT_SECRET`、`TURNSTILE_SECRET`、`SECRETS_MASTER_KEY` 存在 Cloudflare 后台 Secrets，发布流程不覆盖。

## 2. 需要配置的仓库项

路径均为：仓库 → **Settings** → **Secrets and variables** → **Actions**。

### 2.1 Secrets（必填）

| 名称 | 说明 |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Cloudflare API Token，需含 Workers 脚本编辑、D1、KV、R2 权限 |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账户 ID |

### 2.2 Variables（可选）

| 名称 | 说明 |
|---|---|
| `SITE_URL` | 站点主域名**兜底**，必须为 `https://` 开头的纯域名（无路径、无结尾斜杠）。实际主域名优先取后台「站点设置 → 站点网址」；两处都未配置时对外链接回落当前请求域名。多域名绑定下建议只配后台 |
| `TURNSTILE_SITEKEY` | Turnstile 前端 sitekey。未设置时前端不渲染人机验证组件，不影响部署 |
| `CLOUDFLARE_DEPLOY` | **发布总开关**，见 §3 |

## 3. 发布总开关 CLOUDFLARE_DEPLOY

### 3.1 语义

判定条件是 `vars.CLOUDFLARE_DEPLOY != 'false'`，作用于 `ci` 与 `deploy` 两个 job：

| 变量状态 | 结果 |
|---|---|
| 未创建 | **默认发布**，行为与未加开关时完全一致 |
| `true` | 正常发布 |
| `false` | `ci` 与 `deploy` 全部 skipped，不消耗 runner 分钟，不产生失败通知 |
| 其他值（如 `0`、`no`） | 视同未关闭，仍会发布（只有字面量 `false` 才算关闭） |

选择「默认发布」是为了避免忘记开启导致站点长期不更新；需要临时停发布时显式关闭。

### 3.2 操作

**关闭发布**：Settings → Secrets and variables → Actions → **Variables** 标签 → **New repository variable** → Name 填 `CLOUDFLARE_DEPLOY`，Value 填 `false`。

**恢复发布**：把该变量值改为 `true`，或直接删除该变量。

快捷入口：`https://github.com/<owner>/<repo>/settings/variables/actions`

注意：变量名只能包含字母、数字、下划线，不能以数字或 `GITHUB_` 开头；Variable 的值在日志中明文可见，只放非敏感内容。

### 3.3 与其他「不发布」方式的区别

| 方式 | 表现 | 适用场景 |
|---|---|---|
| `CLOUDFLARE_DEPLOY=false` | 整条流水线 skipped（灰色） | 主动、计划性停发布 |
| 不填 Secret | 门禁跑完后在「前置检查」步骤**红色失败**，并提示缺少哪个 Secret | 配置错误，需要显眼告警 |

两者是有意区分开的：前者是「明确地不发布」，后者是「以为能发布但没配好」。因此「前置检查」步骤保留，未删除。

## 4. 触发方式

### 4.1 自动触发

推送到 `main` 分支即触发完整发布。并发组 `deploy-production` 且 `cancel-in-progress: false`，多次推送会排队依次执行，不会互相打断。

### 4.2 手动触发

仓库 → **Actions** → 左侧 **Deploy to Cloudflare** → **Run workflow**，可选参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `run_seed` | `false` | 执行 `seed/seed.sql`（初始版块 + 首管，幂等） |

D1 迁移不需要参数：每次运行都会自动应用（`push` 触发时同样执行），无需勾选任何选项。`push` 触发时 `run_seed` 恒为空，因此日常发布不会改动业务数据。

## 5. 首次上线流程

1. 配置 §2.1 的两个 Secrets。
2. 绑定域名后在后台「站点设置 → 站点网址」填写主域名（邮件链接、SEO 规范链接/站点地图、支付回跳均使用它）；需要配置即生效、免 redeploy。`SITE_URL` 变量仅作兜底。
3. Actions → Deploy to Cloudflare → Run workflow，勾上 `run_seed`（建表迁移会自动应用，无需勾选）。
4. 首次运行时流水线会自动 `wrangler d1 create freeidx` 与 `wrangler kv namespace create freeidx-cache`（若不存在）。
5. R2 桶 `freeidx-files` 需自行创建；生命周期规则流水线会尝试自动配置，失败只告警。
6. 在 Cloudflare 后台为 Worker 配置运行时 Secrets：`JWT_SECRET`、`TURNSTILE_SECRET`、`SECRETS_MASTER_KEY`。

之后日常只需推 `main`。

## 6. 常见问题

**流水线显示 skipped，站点没更新？**
检查 `CLOUDFLARE_DEPLOY` 是否为 `false`。

**红色失败并提示「缺少 Secret CLOUDFLARE_API_TOKEN」？**
Secrets 未配置或名字拼错（Secrets 与 Variables 是两个不同标签页，注意不要建错位置）。

**R2 生命周期配置失败？**
`wrangler r2 bucket lifecycle set` 需要 Token 含 Workers R2 Storage Write 权限。该步骤失败只打 warning，不阻断发布；也可手动到 Dashboard → R2 → `freeidx-files` → Settings → Object Lifecycle Rules 添加「前缀 `tmp/`、1 天过期」。

**CI 会跑几遍？**
[ci.yml](../.github/workflows/ci.yml) 自身在 `push: main` 与 `pull_request` 时触发，`deploy.yml` 又通过 `workflow_call` 复用一次，所以推 `main` 时会出现两轮。把 `CLOUDFLARE_DEPLOY` 设为 `false` 只会省掉 deploy 里那一轮，独立 CI 仍会运行。

**为什么本地 `wrangler dev` 正常，线上却找不到数据库？**
`wrangler.toml` 里的 `database_id` / KV `id` 是占位值，属于设计如此：只有 CI 会在构建工作区回填真实 ID，因此部署必须走流水线，不要本地直接 `wrangler deploy`。
